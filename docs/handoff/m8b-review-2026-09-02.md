D-023 구현(`HandleConflict`)도 지시서 §2 권장 ①~④ 그대로다: 갈라진다 · force 미노출 · 미전송을 새 큐 seq 1..n 으로 (`SyncQueue.Reset(choices, events)`) ·
`forkedFrom.sceneIndex = SyncedSceneCount`(마지막 200 시점의 장면 수 = 서버가 받아 준 자리) · `ConflictForked` 이벤트. 옛 큐는 `Discard` 로 비워
시작 시 순회가 같은 409 를 또 맞지 않는다. 충돌 뒤 재동기화는 `TrySyncAsync` 의 합치기(`_syncAgain`)를 타서 같은 흐름 안에서 POST(갈래)→PUT(revision 1) 이 이어진다 — 잘 짜였다.

## 2. 검증 전에 고칠 것 둘 — 둘 다 "동시에 두 번" 문제

### 2-1. 시작 동기화가 fire-and-forget 이라 4번·5번과 경쟁한다 (B-5 §4 에서 터진다)

`VNAppBootstrap.Start` 가 `_ = _saveCoordinator.SyncPendingAsync()` 로 던지고 타이틀을 연다. 새 기기(§4)에서 복구가 HTTP 몇 번을 도는 사이에
4번을 누르면 `GetResumePoint` 가 **아직 비어 있는** 저장소를 읽어 새 게임으로 가고, 그 뒤 복구가 파일을 쓰면서 활성 포인터가 엇갈린다.
시작 시 409(`HandleConflict` 가 활성 파일을 바꿔 쓰는 중)도 같은 창이 있다.

고치는 자리는 하나 — **시작 동기화 Task 를 붙들고, 진행을 시작하는 두 경로가 그것을 먼저 기다린다.**

```csharp
// SaveCoordinator
public Task StartupSync { get; private set; } = Task.CompletedTask;
public Task SyncPendingAsync() => StartupSync = SyncPendingCoreAsync();   // 기존 본문을 Core 로

// VNAdvanceInputPoller.StartProgression / StartNewGame 맨 앞
await _saveCoordinator.StartupSync;
```

"실행 순서는 명시적으로"의 그 자리다. 타이틀 화면이 열려 있는 채로 기다리는 것이라 사용자에게 보이는 차이는 없다(로컬호스트 1초 미만).

### 2-2. `GuestSession.EnsureTokenAsync` 가 동시에 두 번 들어가면 게스트 계정이 둘 생긴다

`SyncPendingAsync` 안에서 `_ = _bookmarkSync.SyncAllAsync()` 는 안 기다리고 바로 `await _server.TrySyncAsync(...)` 로 간다. 둘 다 `CallAsync → EnsureTokenAsync` 인데
`_account == null` 이면 **둘 다 `SignUpAsync`** 로 들어가 게스트 계정을 둘 만들고, 뒤의 `Persist` 가 앞 것을 덮는다 — 회차는 계정 X 밑에, 즐겨찾기는 Y 밑에.
`account.json` 만 없고 로컬 데이터는 있는 경우라 좁지만, 검증 §4·§5 가 정확히 `saves\`·`account.json` 을 옮기는 절차라 밟기 쉽다.
플레이 중 `CreateBookmark → PushAsync` 와 fold 의 `TrySyncAsync` 도 같은 쌍이다(토큰 만료 순간이면 로그인 둘 — 이쪽은 무해).

고치는 자리 둘, 둘 다 한다:

```csharp
// (a) SaveCoordinator.SyncPendingAsync — 문서에 적은 순서("복구 → 옛 큐 → 즐겨찾기 → 활성")대로 기다린다
if (_bookmarkSync != null)
    await _bookmarkSync.SyncAllAsync();

// (b) GuestSession — 토큰 확보를 단일 비행으로. 누가 몇 번을 부르든 가입·로그인은 한 번.
//     기존 EnsureTokenAsync 본문을 EnsureTokenCoreAsync 로 옮기고 이 껍데기를 앞에 둔다.
private Task<string> _ensuring;

public async Task<string> EnsureTokenAsync()
{
    if (HasUsableToken())
        return _account.Token;

    if (_ensuring == null)
        _ensuring = EnsureTokenCoreAsync();

    try { return await _ensuring; }
    finally { _ensuring = null; }     // 여러 대기자가 각자 null 로 두는 것은 무해하다 — 다음 호출은 HasUsableToken 이 먼저 답한다
}
```

(b) 가 있으면 (a) 는 순서를 문서와 맞추는 뜻만 남지만, 둘 다 싸다.

## 3. 검증 뒤 정리할 것 둘 — 막지 않는다

- **옛 회차 큐의 409 를 영구 재시도한다** (`m8b-handoff.md` §3 첫째). 매 시작마다 같은 409 를 맞고 경고를 남긴다 — 끝이 없는 상태다.
  자연스러운 마무리는 **그 회차도 갈라 두는 것**: `HandleConflict` 와 같은 일(새 guid·`forkedFrom`·미전송을 새 큐로)을 활성만 안 바꾸고 한다.
  서버 비용 0, 클라도 있는 코드의 재사용이라 작다. 첫 버전은 지금대로 가되 M9 후보로 적어 둔다 — 최소한 큐 파일에 `ConflictedAt` 을 적어 두 번째부터는 건너뛰는 편이 낫다.
- **409 갈래는 시간을 다시 나누지 않는다.** `ForkFromScene` 은 `Inherited = PlaySecondsAtEntry, Own = 0` 으로 새로 세는데 `HandleConflict` 는 둘을 그대로 둔다.
  목록·통계에서만 보이는 차이라 급하지 않다. 한 줄이면 맞출 수 있다: `k = SyncedSceneCount < Scenes.Count` 이면 `Inherited = Scenes[k].Checkpoint.PlaySecondsAtEntry, Own = PlaySeconds − Inherited`.

## 4. 지시서와 다르게 한 것 — 전부 타당

- 옛 회차 409 를 갈라지 않음(§3 첫째) — 첫 버전 범위 조정으로 받아들인다.
- label·preview 클라 절단 — 서버가 400 을 내는 것보다 낫다.
- 즐겨찾기 스냅샷에 `SyncedAtUtc`·`SyncError` 가 같이 실린다 — 서버는 열지 않고 복구가 덮어쓰므로 무해.
