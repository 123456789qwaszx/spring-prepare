# M8-B 작업 지시 — Unity (`ked-presentation-runtime`)

> 보내는 쪽: 서버(spring-prepare, M8-A 검증·커밋 완료 2026-09-02). 받는 쪽: Unity 작업자.
> 계약 정본: [`server-2026-09-02.md`](server-2026-09-02.md) — 원문 핸드오프 §4 의 "요구"는 제안이었고, 이 답신이 **서버가 실제로 구현해 검증한 것**이다. 둘이 다르면 답신이 이긴다.

## 0. 시작하기 전에 — 계획 대조 (코드보다 먼저)

이미 계획이 있다고 들었다. 그 계획을 버리라는 게 아니라, **답신과 한 번 대조해서 어긋나는 곳을 먼저 말해 달라**는 것이다.
아래 표의 왼쪽(F6-1~B-7)에 자기 계획의 항목을 붙여 보고, ① 답신에 없는 걸 서버에 기대하는 항목, ② 답신이 "안 한다"고 한 걸
하려는 항목, ③ 순서가 다른 항목 — 이 셋만 골라 한 줄씩 보내면 된다. 그게 오면 서버 쪽이 답하고, 그다음 코드에 들어간다.

특히 답신에서 **실측으로 고친 곳 둘**은 계획이 그 전 문서를 보고 짜였을 수 있으니 꼭 확인:
- **F46** — 응답의 null 은 키가 빠지는 게 아니라 `"forkedFrom": null` 처럼 키가 있고 값이 null 이다. Newtonsoft 라 `== null` 분기면 된다. "키 존재로 분기" 하는 코드를 짜지 않는다.
- **F47** — 지금 `ServerApi.CreatePlaythrough`(본문 없음)는 이 서버에서 **400 `MALFORMED_JSON`** 을 받는다. 고장이 아니라 F6-1 전의 예상된 상태.

## 1. 순서 — 왜 이 순서인가

| 순서 | 항목 | 왜 여기인가 | 끝났다는 증거 |
|---|---|---|---|
| 1 | **F6-1** 회차 생성에 `clientPlaythroughId`·`forkedFrom` 동승 | 이게 없으면 모든 회차 POST 가 400 이라 동기화 전체가 죽어 있다. 다른 어떤 것도 이것 없이는 검증이 안 된다 | 서버 켜고 4번 → 콘솔 `회차 생성 — playthroughId N` + 응답의 `clientPlaythroughId` 가 로컬 guid 와 같다. **5번 두 번** → 두 번째 회차도 201. 앱 껐다 켜서 4번 → 같은 guid 로 POST 가 **200** 이고 같은 N |
| 2 | **F6-2** PUT 에 `inheritedPlaySeconds`·`ownPlaySeconds`·`chapterCompleted` | 필드 셋 추가뿐. 안 보내면 서버가 0/0/false 로 세우므로 급하지 않지만 싸다 | `GET /users/{uid}/playthroughs` 의 슬롯 1 값이 로컬과 같다 |
| 3 | **F6-4** 시작 시 **모든 회차 큐** 순회 | 갈라지기(F6-1)가 들어오는 순간 옛 회차 큐에 미전송이 남을 수 있다(D-c). 갈라지기보다 먼저 있어야 안전하다 | 오프라인에서 새 게임(5번) → 온라인 재시작 → 옛 회차의 `choice_history` 가 서버에 채워진다 |
| 4 | **F6-3** 즐겨찾기 PUT·DELETE 직접 | 큐 없이. 실패하면 다음 기회(다음 시작·다음 fold)에 다시 PUT — 멱등이라 자유롭다 | PUT 201 → 재시작 후 같은 것 PUT 200. 삭제 204. `GET /users/{uid}/bookmarks` 가 로컬 `bookmarks.json` 과 같다 |
| 5 | **B-5** 복구 — 회차 목록 + 즐겨찾기 목록 GET → 로컬 재구성 | 활성 = `lastSavedAt` 최신(D-e). 서버에 "활성" 개념 없음 | §4 "새 기기" 시나리오 |
| 6 | **B-6** 409 해소 — **D-023** | §2 의 결정대로 | 두 기기 시나리오 |
| 7 | **B-7** `M8-check.md` B 절 작성 → 실행 → 커밋 → 서버 쪽에 답신 | | §5 형식 |

**1 이 끝나면 멈추고 한 번 알려 달라.** 그 시점에 서버가 실물 로그·DB 를 대조한다(M7 §1 과 같은 방식). 거기서 어긋나면 2~6 은 전부 헛수고가 된다.

## 2. D-023 — 409 의 기본 해소 (아미야 결정: ___ )

서버는 M4 그대로다(409 + `force`). 갈라지기는 서버엔 "회차 생성의 한 형태"일 뿐이라 비용 0. **결정은 전부 클라 정책**이고 넷이다:

| # | 물음 | 서버 권장 |
|---|---|---|
| ① | 409 를 받으면 기본으로 무엇을 하나 | **갈라진다.** 아무것도 버리지 않고, 누가 맞는지 고를 필요가 없다 |
| ② | `force`(덮어쓰기)를 클라 UI 에 남기나 | **첫 버전에서는 노출하지 않는다.** 서버엔 남아 있으니 필요해지면 켠다 |
| ③ | 갈라질 때 **진 기기의 미전송 큐**는 | 옛 큐의 미전송 선택을 **새 회차의 seq 1..n 으로 다시 번호 매겨** 새 큐로 옮긴다. `forkedFrom.sceneIndex` = 마지막으로 서버가 받아 준 장면. 스냅샷은 새 회차 슬롯 1 에 `baseRevision 0` 으로 |
| ④ | 사용자가 시키지 않았는데 회차가 둘이 된 것을 어떻게 보이나 | 목록에 갈래 표시(`forkedFrom` 있음) + 한 줄 안내. 서버 `forkedFrom.sceneIndex` 가 그 자리다 |

③ 이 핸드오프의 "새 guid + 빈 큐" 만으로는 덮이지 않는 부분이다 — 빈 큐로 시작하면 진 기기의 마지막 장면 선택이 사라진다.
아미야가 위 표의 빈칸을 채워 주면 그대로 D-023 결정문이 된다. **B-6 은 이 결정 없이 시작하지 않는다.** 1~5 는 결정과 무관하다.

## 3. 지켜야 할 것 (서버 쪽에서 본 경계)

- `clientPlaythroughId`·`clientBookmarkId` = **Guid "N"(32 hex)**. 서버는 32자까지만 받는다. 다른 형식으로 바꾸지 않는다.
- `forkedFrom.playthroughId`(서버 id)는 **보내지 않는다** — 서버가 읽지 않는다(답신 §3-2). `clientPlaythroughId` + `sceneIndex` 만.
- 회차 POST 의 **200 과 201 은 둘 다 성공**이다. `playthroughId` 만 받아 쓴다. 201 을 기다리는 분기를 만들지 않는다.
- **도착 순서를 맞추려 하지 않는다.** 자식이 부모보다 먼저 가도 서버가 나중에 잇는다. 부모 POST 를 기다리는 코드를 넣지 않는다 — D-c 의 best-effort flush 만.
- 즐겨찾기에는 **409 처리를 만들지 않는다.** revision 이 없다. 마지막 PUT 이 이긴다.
- **413** 은 "줄여 보내라"다. 재시도하지 않는다. 백로그 300줄 상한이면 닿지 않으니, 닿으면 상한이 깨진 것이다 — 로그로 드러낸다.
- PUT 의 `choices` 는 **지난 PUT 이후의 것만** 싣는다(seq 이어짐). 서버는 부분 겹침을 걸러 주지 않는다 — 전부 겹치면 replayed, 하나라도 새것이면 붙인다(D-010).
- 서버에 새 요구가 생기면 코드로 우회하지 말고 **한 줄로 적어 보낸다** — DECISIONS 에 번호가 붙고 나서 서버가 바뀐다.

코드 스타일은 M7 리팩터링 때 세운 것 그대로: **검증은 경계(`ServerApi`·런처)에서 한 번 → 안은 신뢰 → 실행 순서는 직접 호출로 명시 → 아는 값을 버렸다 재계산하지 않는다.** 호스트 코드 네임스페이스 없음, 주석 짧게, 문서 번호(D-xxx·F6-n)를 코드 주석에 넣지 않는다.

## 4. 검증 시나리오 — `M8-check.md` B 절이 담아야 할 것

서버는 `bootRun` 으로 켜 둔다(`game` DB, V6 적용됨). 모든 DB 질의는 **이번 계정의 userId 로 거른다**(seed 와 지난 검증 행이 있다).

1. **F6-1 스모크** (§1 순서 1 의 증거) — 4번, 5번×2, 재시작 4번(200).
2. **갈라지기 왕복** — 장면 몇 개 진행 → 갈라지기 → 두 회차 모두 서버 목록에, 자식의 `forkedFrom` 이 채워져 있다. 옛 회차 큐의 마지막 장면이 서버에 있다(F6-4).
3. **즐겨찾기 왕복** — 찍기·삭제·재시작 후 서버 목록과 로컬이 같다.
4. **새 기기 복구** — `%USERPROFILE%\AppData\LocalLow\<Company>\<Product>` 를 비우고 **`account.json` 만 되돌려 놓는다**(게스트 계정이라 이게 "같은 사람의 새 기기"를 흉내 내는 유일한 방법이다, D-016). 시작 → 회차·즐겨찾기가 서버에서 내려와 재구성되고 활성이 `lastSavedAt` 최신이다. 이어서 진행이 된다.
5. **두 기기 409** — 저장 폴더를 통째로 복사해 둘로 만들고(A·B), A 에서 장면 진행·동기화 → B 에서 다른 장면 진행·동기화 → B 가 409 → D-023 대로 갈라진다. 서버 목록에 회차가 하나 늘고, B 의 미전송 선택이 새 회차 seq 1.. 에 있다(③).
6. 서버 테스트는 손대지 않았으니 116건 그대로 — 클라 작업이 서버 코드를 건드릴 이유가 없다.
