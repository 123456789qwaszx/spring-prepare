# 서버(spring-prepare) 인수인계 — 클라이언트 구조와 요구 사양

2026-09-02. Unity 레포(`ked-presentation-runtime`)의 저장 모델이 굳었다. 서버는 M7(Unity 저장 포트)까지
검증됐고 M8(복구·충돌 UI) 앞이다. 이 문서는 **그 사이에 클라가 무엇을 바꿨고, 서버가 무엇을 받게 되며,
무엇을 정해야 하는지**를 서버 쪽이 파악할 수 있게 쓴 것이다.

원칙은 그대로다 — **서버는 스냅샷을 해석하지 않고, 판단하지 않고, 기록한다.** 아래 요구는 전부 그 원칙 안에 있다.

---

## 0. 한 장 요약

| | M7 때 (서버가 아는 모습) | 지금 |
|---|---|---|
| 재개 단위 | 에피소드(D-017) | **장면 루트** — 세이브는 "장면 진입 스냅샷 또는 챕터 완료" |
| 로컬 파일 | `slot1.json` + `sync_queue.json` | `playthroughs/{id}.json` + `{id}.queue.json` + `active.json` + `bookmarks.json` |
| 회차 | 서버 id 하나 | 로컬 guid + 서버 id. **갈라진 회차**(`forkedFrom`)가 생긴다 |
| 커밋 | 선택마다 즉시 저장·적재 | **장면 끝에 한 번** — 선택 N개가 한 번에 적재(Seq 순서) |
| 롤백 | 에피소드 안 | 장면 안 어디로든. **확정된 것(이전 장면)은 되돌리지 않고 갈라진다** |
| 세이브/로드 | 슬롯 | **즐겨찾기**(이력 위의 점, 사본) + **갈라지기**(물려받아 새 회차) |
| 스냅샷 | 위치·스탯 | 위치·스탯·[3] 변수·장면 기록 이력·백로그·두 종류 시간 |
| 서버 계약 | M2~M6 그대로 | **M2~M6 그대로 + 아래 §4 추가**. 되감기 표식 같은 것은 없다 |

## 1. 클라이언트 구조 (서버가 알아야 할 만큼만)

### 1.1 세 상태 계층 (변화 없음)

- [1] 영구 — 아직 없음(서버 `event_log`가 그 그릇).
- [2] 진행 스탯 — `ProgressionState`. 간선 커밋만이 바꾼다. 서버 `choice_history`가 그 이력.
- [3] 연출 변수 — Yarn 저장소. 챕터 로컬. **이제 스냅샷에 통째로 실린다**(`Variables`).

### 1.2 장면(Scene) — 새 경계

챕터 JSON의 `Nodes[].SceneId`로 에피소드를 묶는다(비면 에피소드 하나 = 장면 하나). 장면 안에서는
무대·롤백·선택 기록이 이어지고, **장면이 끝날 때 한 번에 확정(fold)**되어 저장·적재된다.
서버 입장에서 달라지는 것: `PUT /saves` 한 번에 `choices`가 여러 개(그 장면의 경로), `events`도
그 장면 것이 모여 온다. seq는 여전히 연속.

### 1.3 회차와 갈래

- 회차 = 한 줄의 타임라인. 로컬 guid로 파일이 산다. 서버 id는 그 회차의 큐 파일이 든다(지금과 같다).
- **갈라지기** = 이력의 한 점(장면 진입 스냅샷 + 그 장면 안 경로)을 물려받아 **새 회차**를 시작.
  옛 회차는 그대로 남고(파일도, 서버 row도), 새 회차의 선택 seq는 1부터.
- 즐겨찾기 = 그 점의 **사본**(스스로 완결). 로드 = 즐겨찾기로 갈라지기.
- "확정된 것은 되돌리지 않는다. 대신 갈라진다." — 그래서 v1에서 검토했던 되감기 표식(superseded)은 **없다**.

### 1.4 동기화 흐름 (M7과 같고, 갈라지기가 하나 더)

```
[활성 회차의 큐]  fold → 로컬 저장 1회 → EnqueueChoice×N, EnqueueEvent×M → TrySync
TrySync          토큰 → (서버 회차 없으면 POST 생성) → 챕터 버전(checksum) → 배치 캡처 → PUT → Ack
갈라지기         옛 회차 큐 그대로 둠 → 새 회차 파일·새 큐(비어 있음, 서버 id 없음) → 다음 fold의 TrySync가 POST로 새 서버 회차 생성
```

주의: 지금은 **회차 생성 POST가 멱등이 아니다**(재시도하면 서버 회차가 둘). 갈라지기로 생성이 잦아지니
§4 R1의 `clientPlaythroughId`가 필요하다.

## 2. 서버가 받게 되는 데이터

### 2.1 `PUT /playthroughs/{pid}/saves/1` 본문 (지금 형식 + 추가 후보)

| 필드 | 지금 | 뜻 |
|---|---|---|
| `chapterId`, `chapterVersion`, `currentEpisodeId`, `playSeconds`, `deviceKey`, `baseRevision` | 있음 | 그대로. `currentEpisodeId`는 **항상 장면 루트**(또는 챕터 완료면 마지막 에피소드) |
| `snapshot` | 있음 | `LocalSaveFile` 통째(§2.2). **열지 않는다** |
| `choices[]`, `events[]` | 있음 | 그 장면에서 확정된 것 전부. seq 연속 |
| `inheritedPlaySeconds`, `ownPlaySeconds` | **추가 후보** | 목록·통계용. `playSeconds`는 둘의 합 |
| `chapterCompleted` | **추가 후보** | 목록용. 스냅샷을 열지 않고 "끝낸 회차"를 그리려면 필요 |

### 2.2 스냅샷(`LocalSaveFile`)의 모양 — 참고용, 서버는 해석하지 않는다

```
PlaythroughId(로컬 guid) · ForkedFrom{PlaythroughId, SceneIndex, Target{NodeName, LineId, Occurrence}}
ChapterId · CurrentEpisodeId · Stats{} · Variables{Floats, Strings, Bools} · ChapterCompleted
Scenes[]   장면 기록 = Checkpoint{루트·Stats·Variables·백로그 순번·마지막 seq·진입 시 시간} + Path[] + YarnChoices[] + 순번 끝
Backlog[]  현재 장면 이전의 대사 항목(상한 300줄)
PendingLoad{Path, YarnChoices, Target}  갈라진 직후 한 장면 동안만
InheritedPlaySeconds · OwnPlaySeconds · PlaySeconds · SavedAtUtc
```

**크기.** 백로그 300줄 × 한글 대사 ≈ 30~60KB, 장면 기록은 챕터 안 장면 수에 비례. MySQL `JSON` 컬럼에는
무리 없지만 서버가 상한을 두려면 §5 D-f.

### 2.3 즐겨찾기(`Bookmark`) — 새 종류의 스냅샷

```
Id · Label · Preview · CreatedAtUtc · PlaythroughId(출처 로컬 guid) · SceneIndex · ChapterId
Checkpoint · Load{Path, YarnChoices, Target} · Backlog[] · PlaySecondsAtBookmark
```
스스로 완결된 사본이라 출처 회차 파일이 없어도 로드된다. 수 제한 없음(100개 이상 전제).

## 3. 서버가 바꾸지 않아도 되는 것

- `choice_history (save_slot_id, seq)` UNIQUE, 재전송 흡수, 409 낙관적 동시성(M4) — 그대로.
- `event_log (playthrough_id, event_key)` UNIQUE(D-011) — 그대로. 장면 끝에 몰려 와도 같은 규칙.
- 챕터 버전 대조(D-015, checksum) — 그대로. 즐겨찾기도 같은 버전 대조를 받는다(§4 R3).
- 슬롯 번호 — 회차당 `slot_no = 1` 하나만 쓴다. 1~127 허용(D-008)은 그대로 두되 클라는 1만 쓴다.

## 4. 요구 (서버 작업 후보)

| # | 요구 | 테이블/엔드포인트 | 근거 |
|---|---|---|---|
| R1 | 회차 생성을 **멱등**으로, 출처를 받는다: `POST /users/{uid}/playthroughs { clientPlaythroughId, forkedFrom?: { playthroughId?(서버 id), clientPlaythroughId, sceneIndex } }`. 같은 `(user_id, client_playthrough_id)`면 기존 row 반환(200) | `playthroughs`에 `client_id VARCHAR(32)` UNIQUE(user_id, client_id), `forked_from_id BIGINT NULL` FK self, `forked_from_client_id VARCHAR(32) NULL`, `forked_scene_index INT NULL` | 갈라지기가 생성을 잦게 하고, 재시도가 회차를 두 개 만들면 안 된다. 부모가 아직 서버에 없을 수 있어(오프라인) 클라 id를 함께 받는다 |
| R2 | 갈라진 회차의 `choice_history`는 seq 1부터 — 부모 것을 복사하지 않는다 | 변화 없음 | 회차마다 선형. 집계는 `forked_from_id` 유무로 나눠 센다 |
| R3 | 즐겨찾기: `PUT /users/{uid}/bookmarks/{clientBookmarkId} { label, preview, chapterId, chapterVersion, playthroughClientId?, sceneIndex, createdAt, snapshot }` · `GET /users/{uid}/bookmarks` (메타만) · `DELETE`. 스냅샷은 열지 않는다 | 새 테이블 `bookmarks(id, user_id, client_id UNIQUE(user_id, client_id), chapter_content_id FK, playthrough_id NULL, scene_index, label, preview, snapshot JSON, created_at, updated_at, deleted_at NULL)` | 다른 기기 복구(M8). **유저 소유** — 회차가 아니라 유저에 매달린다(사본이니 출처 회차가 없어도 산다) |
| R4 | 회차 목록 `GET /users/{uid}/playthroughs`에 `forkedFrom`, `chapterId`, `currentEpisodeId`, `chapterCompleted`, `inheritedPlaySeconds`, `ownPlaySeconds`, `bookmarkCount`, `lastSavedAt` | `save_slots`에 `inherited_play_seconds INT`, `own_play_seconds INT`, `chapter_completed BOOL` (PUT 본문에서 받아 저장) | 이력 화면·M8 복구 화면을 스냅샷 없이 그린다 |
| R5 | 슬롯은 회차당 1개로 쓴다는 것을 문서에 — 상한(127)은 그대로 | 변화 없음 | 즐겨찾기가 슬롯을 대체했다 |
| R6 | 시작 시 **여러 회차의 큐를 순서대로** 동기화할 수 있어야 한다(같은 유저, 다른 회차) | 변화 없음 — 회차별 PUT이 독립이면 된다 | 갈라진 뒤 옛 회차 큐에 미전송이 남을 수 있다(§5 D-c) |
| R7 | `ended_at`은 손대지 않는다. 챕터 완료는 `chapter_completed`로 온다 | 변화 없음 | "끝낸 회차"와 "닫은 회차"는 다르다 |

## 5. 논의·결정이 필요한 것

| # | 질문 | 내 권장 | 이유 |
|---|---|---|---|
| D-a | 즐겨찾기를 어디에 매다나 — 유저 vs 회차 | **유저** | 사본이라 출처 회차가 지워져도 산다. 회차에 매달면 갈라진 회차마다 흩어진다 |
| D-b | 부모 회차가 서버에 아직 없을 때(오프라인 갈라지기) `forkedFrom`을 어떻게 받나 | 클라 id를 받아 두고, 부모가 뒤에 생성되면 서버가 `forked_from_id`를 채운다(또는 조회 시 조인) | 클라가 순서를 보장할 수 없다. 서버가 "모르는 부모"를 거부하면 갈라진 회차가 영영 못 올라간다 |
| D-c | 갈라진 뒤 **옛 회차 큐에 남은 미전송** | 클라: 갈라지기 전에 현재 큐를 best-effort flush(지금 새 게임이 하는 것과 같게) + 시작 시 모든 회차 큐를 순회 동기화(R6). 서버: 아무것도 안 함 | 옛 회차의 마지막 장면 선택이 서버에 빠지면 그 회차의 이력이 짧게 남는다. 판단은 서버가 아니라 클라의 전송 책임 |
| D-d | 통계에서 갈래를 어떻게 세나 | `forked_from_id IS NULL`을 "회차 수", 전체를 "갈래 수". 선택 비율(M5)은 회차마다 선형이라 그대로 | 되감기 표식이 없어 superseded 제외 로직이 필요 없다 |
| D-e | M8 복구: 새 기기에서 무엇을 내려받나 | 회차 목록(R4) + 즐겨찾기 목록(R3). 클라가 "가장 최근 저장된 회차"를 활성으로 두고 나머지는 접힌 목록으로 | 서버에 "활성" 개념을 두지 않는다 — 기기마다 다를 수 있다 |
| D-f | 스냅샷·즐겨찾기 크기 상한 | 1MB 초과 시 413. 클라는 백로그 300줄 상한으로 그 아래에 머문다 | JSON 컬럼은 여유 있지만 무한은 곤란 |
| D-g | 즐겨찾기 삭제 | soft delete(`deleted_at`) — 목록에서 빼고 row는 남긴다 | 회차 파일을 안 지우는 것과 같은 결. 복구 가능 |
| D-h | 챕터 버전이 다른 즐겨찾기 로드 | 서버는 `chapter_content_id`만 기록. 클라가 대조해 "루트에서 시작"으로 퇴행(D-017의 결) | 서버는 판단하지 않는다 |

## 6. 클라이언트가 F6에서 할 일 (서버가 위를 반영하면)

1. 회차 생성에 `clientPlaythroughId`·`forkedFrom` 동승 (R1). 갈라지기 전 현재 큐 flush (D-c).
2. `PUT /saves/1` 본문에 `inheritedPlaySeconds`·`ownPlaySeconds`·`chapterCompleted` (R4).
3. 즐겨찾기 업로드·삭제 동기화 (R3). 큐 없이 스냅샷 직접 PUT — 실패하면 다음 기회에.
4. 시작 시 모든 회차 큐 순회 동기화 (R6).
5. M8: 회차·즐겨찾기 목록 GET → 로컬 재구성.

## 7. 순서도

**장면 끝(fold) → 동기화** (지금과 같다, 선택이 여럿일 뿐)
```
SceneRunner.FinalizeScene → SaveCoordinator.ReportSceneCommitted
  → 로컬 저장(playthroughs/{id}.json)      # 먼저
  → EnqueueChoice × N, EnqueueEvent × M   # 그다음
  → TrySync: 토큰 → 서버 회차 확인/생성 → 챕터 버전 → PUT /playthroughs/{pid}/saves/1 → Ack
```

**갈라지기 → 첫 동기화**
```
ForkFromScene/ForkFromBookmark → 새 파일(ForkedFrom, 물려받은 것) → active.json → 새 큐(빈, 서버 id 없음)
… 새 회차의 첫 fold → TrySync: 서버 회차 없음 → POST /playthroughs { clientPlaythroughId, forkedFrom } → PUT
```

**즐겨찾기** (F6)
```
CreateBookmark → bookmarks.json → PUT /users/{uid}/bookmarks/{clientId} (스냅샷 통째)
```
