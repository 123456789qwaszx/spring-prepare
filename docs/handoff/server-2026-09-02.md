# 서버 → 클라이언트 답신 — M8-A 반영 결과와 F6 계약 확정

> 원문: [`unity-2026-09-02.md`](unity-2026-09-02.md). 서버 코드 반영 2026-09-02 (V6, 32파일). 검증: [`../M8-check.md`](../M8-check.md) §A.
> 이 문서는 **F6 이 붙잡을 계약의 정본**이다. 여기 없는 것은 M2~M7 계약 그대로다.

## 0. 한 장 요약

요구 R1~R7 을 전부 받았다. 서버가 바뀐 것은 셋 — **회차 생성이 멱등**이 됐고 부모를 받으며(R1), **세이브 PUT 에 선택 필드 셋**이
늘었고(R4), **즐겨찾기 4 엔드포인트**가 생겼다(R3). 나머지(R2·R5·R6·R7)는 "바뀌지 않는다"를 테스트로 확인했다.
결정 D-a~D-f 는 전부 제안대로 갔고, 둘을 **정정**했다(§3). 크기 상한은 413 이다(D-f).

**F6 전의 클라는 회차 생성에서 400 을 맞는다** — 지금 `ServerApi.CreatePlaythrough` 는 본문·Content-Type 없이 POST 하고, 서버는 그것을 "본문 없음"(`MALFORMED_JSON`)으로 본다. 본문을 `{}` 로 보내면 400 `BAD_REQUEST`(`clientPlaythroughId` 필수, D-019). (PowerShell 로 흉내 내면 415 — PS 가 form Content-Type 을 붙여서다, F47.) 어느 쪽이든 의도한 단절이다 — F6-1 이 먼저다.

**검증 결과 (09-02)**: 서버 테스트 115건(정정 뒤 116) + M8-check §1~§6 PowerShell 전부 통과. 아래 계약은 실측으로 고친 정정본이다 — 특히 §1.4 의 **null 규칙**.

## 1. 확정된 계약

### 1.1 `POST /users/{uid}/playthroughs` — 멱등 (R1, D-019·D-020)

```jsonc
// 요청 (Content-Type: application/json, Bearer 토큰)
{ "clientPlaythroughId": "32hex",                    // 필수. Guid "N". 길이 ≤ 32
  "forkedFrom": {                                    // 갈래일 때만
      "clientPlaythroughId": "32hex",                // 필수 (갈래면)
      "sceneIndex": 3                                // 필수, ≥ 0
      /* "playthroughId": 서버 id — 보내도 되지만 서버는 읽지 않는다 (§3-2) */ } }

// 응답
201 Created  Location: /playthroughs/{id}/saves   { "playthroughId": 27, "clientPlaythroughId": "32hex" }   // 새로 만듦
200 OK                                            { "playthroughId": 27, "clientPlaythroughId": "32hex" }   // 이미 있었음 — 본문 같음
400 BAD_REQUEST   clientPlaythroughId 없음 / 갈래인데 부모 클라 id 없음 / sceneIndex < 0
400 MALFORMED_JSON   본문·Content-Type 없이 보낸 옛 POST (F6 전 클라 = 지금 Unity). Content-Type 만 JSON 이 아닌 것으로 붙이면 415
```

- 같은 `(userId, clientPlaythroughId)` 는 몇 번을 보내도 회차 하나. 재시도·재설치·다른 기기 전부 같은 답.
- **부모가 아직 서버에 없어도 201** 이다(D-b). 서버는 부모의 클라 id 를 적어 두고, 부모가 도착하는 순간 `forked_from_id` 를 되채운다.
  클라는 **순서를 맞추려 애쓰지 않아도 된다** — 다만 D-c 의 best-effort flush 는 그대로 권한다(옛 회차의 마지막 장면 이력을 위해).
- 갈라진 회차의 `choice_history` 는 seq 1 부터 (R2) — 서버는 부모 것을 복사하지 않는다. 변화 없음.

### 1.2 `PUT /playthroughs/{pid}/saves/{slotNo}` — 선택 필드 셋 (R4)

```jsonc
{ /* 기존 필드 전부 그대로: chapterId, chapterVersion, currentEpisodeId, snapshot, playSeconds, deviceKey, baseRevision, choices[], events[] */
  "inheritedPlaySeconds": 100,   // 선택. 없으면 0
  "ownPlaySeconds": 20,          // 선택. 없으면 0
  "chapterCompleted": true }     // 선택. 없으면 false
```

- `playSeconds` 는 여전히 **둘의 합** — 서버는 검산하지 않는다(클라가 계산한 값 그대로).
- 응답 형식·409·replayed·이벤트 흡수 — **변화 없음.** 장면 단위로 접혀 300 선택이 한 PUT 에 실려도 같다(테스트 `장면_단위로_접힌_큰_배치도_한_요청에_다_들어간다`).
- 슬롯은 회차당 1개로 쓴다(R5) — 상한 127 은 그대로. 목록(§1.4)은 **슬롯 1** 의 값을 싣는다.
- 스냅샷 직렬화 크기가 **1,048,576 바이트를 넘으면 413** (§1.5).

### 1.3 즐겨찾기 (R3, D-021)

전부 `/users/{uid}/bookmarks` 아래 — 본인 토큰만(경로 본인 확인, 남의 것은 403).

```
PUT    /users/{uid}/bookmarks/{clientBookmarkId}     201 신규 / 200 갱신·부활      (멱등 upsert)
GET    /users/{uid}/bookmarks                         200 [ 메타 … ]  (스냅샷 없음, createdAt 순)
GET    /users/{uid}/bookmarks/{clientBookmarkId}     200 메타 + snapshot   /  404 (없거나 삭제됨)
DELETE /users/{uid}/bookmarks/{clientBookmarkId}     204 (soft, 멱등 — 없어도·이미 지웠어도 204)
```

```jsonc
// PUT 요청
{ "label": "갈림길 앞",                 // 필수, ≤ 100
  "preview": "왼쪽으로 갈까",            // 선택, ≤ 200 (없으면 "")
  "chapterId": "qwer", "chapterVersion": 2,   // 필수 — 없는 버전이면 404 (세이브와 같은 규칙, D-015)
  "playthroughClientId": "32hex",        // 선택 — 출처 회차의 클라 id
  "sceneIndex": 4,                       // 필수, ≥ 0
  "createdAt": "2026-09-02T12:00:00Z",   // 선택 — 없으면 서버 시각. 오프셋이 붙어 와도 UTC 로 정규화(D-009)
  "snapshot": { … } }                    // 필수. 열지 않는다. 1MB 초과 413
// PUT 응답
{ "clientBookmarkId": "…", "playthroughId": 27 /* 출처 회차가 서버에 있으면. 없으면 null */, "updatedAt": "…Z" }
// GET 목록의 한 줄 / GET 단건 (단건에만 snapshot)
{ "clientBookmarkId", "label", "preview", "chapterId", "chapterVersion", "playthroughClientId", "playthroughId" /* null 가능 */, "sceneIndex", "createdAt", "updatedAt" [, "snapshot"] }
```

- **revision·baseRevision·409 가 없다.** 사본이라 지킬 누적 상태가 없다 — 마지막 PUT 이 이긴다. 클라는 409 처리를 즐겨찾기에 만들지 않는다.
- 출처 회차가 아직 서버에 없으면 `playthroughId: null` 로 저장되고, 회차가 도착할 때 서버가 채운다(D-020 의 즐겨찾기판). 클라는 신경 쓰지 않는다.
- 삭제는 soft — 같은 `clientBookmarkId` 로 다시 PUT 하면 되살아난다(200). 클라가 "삭제 취소"를 만들 때 쓸 수 있다.
- 단건 GET 의 `snapshot` 은 **키 순서·공백이 바뀌어 돌아온다** (MySQL JSON 컬럼 정규화 — M1·M2 때와 같은 관찰). 의미는 같다. 바이트 비교를 하지 않는다.
- `clientBookmarkId` ≤ 32 (Guid "N").

### 1.4 `GET /users/{uid}/playthroughs` — 확장된 한 줄 (R4)

```jsonc
{ "id": 27, "clientPlaythroughId": "32hex",         // 옛 회차(F6 전·seed)는 null
  "forkedFrom": { "playthroughId": 26, "clientPlaythroughId": "32hex", "sceneIndex": 3 },   // 새 게임이면 forkedFrom: null. playthroughId 가 null 이면 부모 미도착
  "startedAt", "endedAt",                          // 진행 중이면 endedAt: null
  "slotCount": 1, "bookmarkCount": 2,               // bookmarkCount 는 클라 id 로 센다(삭제 제외)
  // ↓ 슬롯 1 의 값. 슬롯이 없으면 이 키들이 전부 null
  "chapterId": "qwer", "chapterVersion": 2, "currentEpisodeId": "EP02_01",
  "chapterCompleted": true, "inheritedPlaySeconds": 100, "ownPlaySeconds": 20, "playSeconds": 120,
  "lastSavedAt": "…Z" }
```

- id 순. 팬아웃 없음(슬롯 둘·즐겨찾기 셋이어도 회차당 한 줄).
- **null 인 필드는 키가 있고 값이 `null` 이다** (F46 — M2 부터 그랬다. "키가 빠진다"고 적었던 곳은 전부 오기). Newtonsoft 는 부재와 null 을 같게 읽으므로 클라는 `== null` 로 분기하면 된다. `endedAt`·`device` 도 같은 규칙.

### 1.5 413 (D-f, D-022)

```
413  { "code": "PAYLOAD_TOO_LARGE", "message": "snapshot 이(가) 상한을 넘었습니다: 1100011 bytes > 1048576" }
```

세이브 PUT 과 즐겨찾기 PUT 둘 다. 서버가 재는 것은 요청 전체가 아니라 **snapshot 을 다시 직렬화한 UTF-8 바이트**다.
413 은 아무것도 쓰지 않는다(revision 그대로). 클라가 할 일은 "고쳐 보내라"가 아니라 "줄여 보내라" — 백로그 300줄 상한이면 닿지 않는다.

### 1.6 `GET /users/{uid}/summary` (D-d)

`forks` 필드 하나 추가 — 갈라진 회차 수. `playthroughs` 는 갈래(줄) 단위 그대로. 뿌리 수 = `playthroughs - forks`.

## 2. 바뀌지 않았다 — 테스트로 확인한 것 (§3 "서버가 바꾸지 않아도 되는 것")

| 원문 | 확인 |
|---|---|
| seq 연속·`(save_slot_id, seq)` UNIQUE·replayed | 300 선택 한 요청 → 다음 장면 이어 붙임 (SaveHistoryApiTest +1) |
| 409 + `force` (D-010) | 코드 무변경. 테스트 8건 그대로 PASSED |
| 이벤트 회차당 1회 흡수 (D-011) | 무변경 |
| D-015 chapterVersion ↔ checksum | 무변경. 즐겨찾기도 같은 규칙(없는 버전 404) |
| `ended_at` (R7) | 손대지 않았다. `chapter_completed` 는 슬롯 열이다 |
| R6 여러 회차 큐 순회 | 회차별 PUT 독립 — 무변경 |

## 3. 원문에서 정정한 것 둘

1. **D-d 뿌리 판정은 `forked_from_id` 가 아니라 `forked_from_client_id` 로 한다.** 부모가 아직 안 온 갈래는 `forked_from_id` 가 NULL 이라
   전자로 세면 뿌리로 잘못 세어진다. 후자는 갈래면 항상 있다. (`user_summary.sql`)
2. **R1 의 `forkedFrom.playthroughId`(서버 id)는 서버가 읽지 않는다.** 소유 검증 없는 숫자를 믿을 이유가 없고, 클라 id 로
   같은 사용자 안에서 찾으면 된다. 보내도 무해하지만 **F6 은 안 보내는 쪽을 권한다** — 클라가 서버 id 를 기억해야 할 이유가 하나 줄어든다.
