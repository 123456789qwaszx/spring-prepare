## 1. 목표와 한 줄 요약

**`ked-presentation-runtime`이 비워둔 `ISaveStore`를 채운다. 로컬 우선, 서버는 동기화.**

끝나면: 비행기 모드에서 선택 5개 → 온라인 → 서버 `choice_history`에 5행(seq 연속). 앱 강제 종료 후 재실행 → 로컬에서 이어지고 큐가 남아 있다.

- [x] **§2-2 새 발견 — 계획이 몰랐던 것 둘** (M7-0 → **D-015 로 해소**, 회차 흐름은 M7-6 에 반영):
  - **클라에 chapterVersion 개념이 없다.** 콘텐츠는 서버가 아니라 **에셋 참조**(TextAsset, `Assets/@Dialogue/ChapterProgression/qwer.progression.json` — VNAppBootstrap 인스펙터)로 실려 있고 버전은 서버가 수입 시 붙이는 값이다. 그런데 세이브 PUT 은 `chapterId+chapterVersion` 필수(M2) — 클라가 자기가 재생 중인 에셋이 서버의 몇 버전인지 알 방법이 필요하다.
  - **회차(playthrough) 개념도 클라에 없다.** 세이브 경로가 전부 `/playthroughs/{pid}/…` 이므로 "새 게임 → POST /users/{id}/playthroughs → pid 로컬 보관" 흐름이 M7 설계에 들어가야 한다 (ServerSyncSaveStore 의 일부).
- [x] 서버 쪽 확인: M3 PUT 형식이 C#에서 만들기 쉬운가 (`chosenAt` ISO-8601 UTC → `DateTime.UtcNow.ToString("o")`). → **확인됨** (M3 §7-1 F28): `Z` 로 보내든 `+09:00` 로 보내든 서버가 UTC로 정규화해 저장한다. 따라서 `DateTimeOffset.Now.ToString("o")` 도 안전하다 — 다만 규약은 `Z` 이므로 `DateTime.UtcNow.ToString("o")` 를 기본으로 쓴다.
- [x] **응답 디코딩**: 서버 응답에는 `charset` 이 없다(JSON 규격상 UTF-8). `UnityWebRequest.downloadHandler.text` 는 UTF-8로 읽으므로 그대로 쓰면 된다. M3 검증에서 PowerShell 이 이것을 ISO-8859-1로 읽어 한글이 깨졌는데, **서버가 아니라 클라이언트의 디코딩 문제**였다 — Unity 쪽에서 한글이 깨져 보이면 같은 자리를 먼저 의심한다. (M6 검증에서 같은 계보의 사건이 둘 더 — 전부 PowerShell 쪽, F45. UnityWebRequest 는 바이트를 그대로 다뤄 해당 없음.)

## 3. 숙련자의 사고흐름

1. **드라이버는 건드리지 않는다.** `ProgressionDriver` 주석대로 "순서를 두 곳에 적으면 갈린다". 저장은 **호스트(`ProgressionLauncher`)가 커밋 이벤트를 받아** 한다. 드라이버가 커밋 사실을 밖에 알리는 최소 훅(이벤트 하나)만 추가하고, 무엇을 저장할지는 호스트가 정한다.
2. **로컬이 진실, 서버는 사본.** 오프라인 플레이가 요구사항이므로 저장은 항상 로컬 파일에 먼저, 서버 전송은 큐에서 비동기. 서버 실패는 게임 진행을 막지 않는다.
3. **큐에 쌓는 것은 "이벤트", 스냅샷은 "최신 하나".** 선택 커밋마다 `{seq, episodeId, optionIndex, chosenAt}`와 EventKey 발생을 큐에 적재. 스냅샷은 덮어쓰기. 그래서 M3 요청이 "증분 choices + 최신 snapshot" 모양이다 — 서버 API가 클라 큐 모양을 결정한 것이 아니라 **그 반대**임을 확인.
4. **seq는 클라가 매긴다.** 슬롯별 단조 증가, 로컬에 영속. 서버 UNIQUE `(save_slot_id, seq)`가 중복을 막는다 (M4). 앱이 죽어도 seq가 되돌아가면 안 되므로 seq 증가와 큐 적재를 한 파일 쓰기로 한다.
5. **스냅샷의 내용은 서버가 모른다.** `{ nodeName, lineId, Yarn 변수, StageState, ProgressionState }` 통째로. 서버는 열지 않는다 (PLAN 1.4). 스냅샷 직렬화 형식은 Unity 쪽 결정 — JSON이면 MySQL JSON 컬럼이 받고, 아니면 base64 문자열로 감싼다 (그러면 PLAN#1을 다시 봐야 한다).
6. **네트워크 계층은 얇게.** `UnityWebRequest` + 토큰 헤더. 재시도는 큐가 남아 있으면 다음 기회에 — 지수 백오프 정도만.

## 5. 특이사항

- **두 레포에 걸친 M.** 서버 레포의 변경은 문서와 (필요 시) API 형식 조정뿐. Unity 쪽 커밋도 conventional 스타일(README 규칙 6)을 따른다.
- **Unity 산출물 21파일** (2026-08-31, 리팩터링 + 아미야 정리 반영): 신설 `Assets/Scripts/Save/` 13파일(`ApiResult` 는 `ServerApi` 에서 분리된 자기 파일) + `Progression/IProgressionReporter.cs`·`ProgressionReports.cs` (전부 Assembly-CSharp — 기존 호스트 코드처럼 **네임스페이스 없음**, asmdef 변경 없음), 수정 6: `ProgressionState`(Restore)·`ResolvedOption`(+SourceIndex)·`ChapterTransition`(서수 전달)·`ProgressionDriver`(reporter 직접 호출, RunAsync 시그니처)·`ProgressionLauncher`(검증 경계)·`VNAppBootstrap`(serverBaseUrl 필드, 저장 스택 조립, Start 에서 잔여 큐 동기화). `.meta` 는 에디터가 처음 열 때 생성되는 것을 커밋하면 된다.
- **리팩터링 원칙** (아미야 리뷰, 08-31): *검증은 경계에서 한 번, 그 뒤는 불변식을 신뢰 / 실행 순서는 명시적으로 / 아는 정보는 버렸다가 재계산하지 않는다.* 이 원칙으로 걷어낸 것 — 드라이버의 `IndexOfOption` 재스캔(→ `SourceIndex`), 이벤트 구독(→ 직접 호출), 드라이버 안의 재개 fallback 셋(→ 런처 한 곳), 코어 `Restore` 의 존재 검사, `ListAll`, 파일 깨짐 try/catch, `AtomicFile` 플랫폼 폴백, 코디네이터의 예외 삼킴, 큐 삭제의 항목별 매칭(→ 접두사 삭제).
- **직렬화 함정 하나를 코드로 봉했다** (`SaveJson`): Newtonsoft 의 `CamelCasePropertyNamesContractResolver` 는 **딕셔너리 키까지** camelCase 로 바꾼다 — 스탯 키("Trust")가 조용히 다른 스탯이 된다. `ProcessDictionaryKeys=false` 인 NamingStrategy 로 멤버 이름만 내린다. 시각은 전부 ISO-8601 UTC **문자열**로 들고 다닌다(Newtonsoft 의 DateTime 자동 파싱 회피, D-009 규약 그대로).
- **타입 검사**: 클라우드에 Unity·dotnet SDK 가 없어(레포지토리 차단) mono `mcs` 로 검사했다 — Unity/Yarn/Newtonsoft 최소 스텁 + `Ked.Progression` 실물 소스(단 target-typed `new()`·`using var` 를 쓰는 파일은 그 부분만 풀어 쓴 사본, mcs 가 C#8·9 를 못 읽어서)로 21파일 중 20파일 컴파일 통과. `VNAppBootstrap` 은 의존이 넓어 제외 — 에디터 컴파일이 검사한다. **아미야가 정리한 최종본 기준으로 재검사 완료** (08-31).
- **아미야 정리분** (리팩터링 뒤 본인이 한 번 더 손봄): `ApiResult` 파일 분리, `PickAsync` 반환을 `ResolvedOption?` 로(내 `default` 센티널보다 낫다 — struct 에 "없음"을 표현하는 정식 수단이다), target-typed `new()`·`using var` 로 레포 스타일 맞춤, 주석에서 `(M7)`·`D-0xx` 같은 문서 참조 제거(코드는 코드만, 결정 근거는 docs 가 맡는다), `ProgressionYarnBridge.BeginChapter` 의 null 가드 제거(같은 원칙의 연장).
- **착수와 함께 서버 잔손질 하나를 처리했다** (F44, 2026-08-31): `JacksonException` → 400 `MALFORMED_JSON` 핸들러 + `ErrorFormatTest` 1건 — 서버 테스트 **97건**. M6 검증에서 실측된 그물 구멍의 마감이다.
- **클라이언트 경험자가 서버를 이해하는 M.** 지금까지의 서버 결정(UNIQUE로 멱등, revision으로 충돌)이 클라 코드에서 어떻게 보이는지 — "seq를 클라가 매긴다"가 그 접점.
- **학습 포인트**: 오프라인 우선 설계, 큐와 멱등 키의 관계, 원자적 파일 쓰기.
