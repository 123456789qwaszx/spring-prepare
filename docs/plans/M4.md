## 1. 목표와 한 줄 요약

**네트워크 재시도와 두 기기 동시 플레이를 락 없이 데이터(revision, UNIQUE)로 처리한다.**

끝나면: 같은 요청을 두 번 보내도 두 번째는 아무것도 쓰지 않고 `replayed=true`, 두 기기가 어긋난 revision으로 올리면 하나만 성공하고 다른 쪽은 409 + 서버 요약, force 재요청은 새 것만 추가한다. 두 스레드 동시 PUT 테스트가 "정확히 하나만 200"을 증명한다.

## 3. 숙련자의 사고흐름

1. **문제를 두 개로 쪼갠다.** (a) *재전송*: 같은 클라가 같은 요청을 다시 보냄 — 응답을 못 받았을 뿐 서버는 이미 적용했다. (b) *충돌*: 다른 기기가 사이에 끼어들었다. 둘 다 "baseRevision ≠ 서버 revision"으로 보이지만 답이 다르다 — (a)는 200, (b)는 409.
2. **재전송을 어떻게 알아보나.** `서버 revision == baseRevision + 1` 이고 동봉 `choices`의 `(save_slot_id, seq)`가 **전부 이미 존재**하면 "내가 방금 적용한 그 요청"이다.
   - `choices`가 비면 판정할 수 없다. **D-010은 그때 200이 아니라 409를 준다** — PLAN 원문과 다른 결론이다. 200을 주면 충돌을 재전송으로 오인해 클라가 "동기화됐다"고 잘못 믿는다. `choices` 없는 PUT이 정상 경로라는 것은 M3 §4.8에서 실측됐다.
   - 구현상 **별도 분기가 필요 없다**: 판정을 못 하면 그냥 조건부 UPDATE 로 넘어가고, base 가 낡았으면 0행 → 409 가 자연히 난다. "판정 불가"를 코드가 특별 취급하지 않아도 답이 맞는 것이 이 설계의 좋은 점이다.
   - 그래서 409 본문에 **현재 서버 상태 요약**을 싣는 것이 중요해진다 — 재전송한 클라가 자기가 보낸 것과 비교해 스스로 판정할 재료다. 그 필드가 M8 충돌 UI가 보여줄 것과 같다.
3. **충돌 감지는 UPDATE 한 줄.**
   ```sql
   UPDATE save_slots SET ..., revision = revision + 1
   WHERE id = :id AND revision = :baseRevision
   ```
   영향 행 수 0 = 누군가 먼저 바꿨다 = 409. 이것이 **낙관적 동시성**이다. `SELECT … FOR UPDATE`(비관적 락)를 쓰지 않는 이유: 충돌이 드물고, 락은 커넥션을 붙들며, 완료 기준의 동시 요청 테스트가 락 없이도 정확함을 증명한다.
4. **순서가 곧 정확성.** 서비스 안: (1) 현재 슬롯 SELECT (없으면 신규 경로) → (2) replayed 판정 → (3) 조건부 UPDATE, 0행이면 409 → (4) choices/events 배치. (3)이 (4)보다 먼저여야 충돌 시 이력이 안 쌓인다. 같은 트랜잭션이므로 (4) 실패 시 (3)도 롤백.
5. **동시성 테스트는 "정확히 하나"를 단언한다.** `ExecutorService`로 두 스레드가 같은 baseRevision으로 PUT → 200 하나, 409 하나. "둘 다 200"이면 조건부 UPDATE가 빠진 것, "둘 다 409"면 첫 SELECT를 트랜잭션 밖에서 하고 있는 것. 이 테스트를 M4 **첫 작업**으로 써 두고(실패하는 상태로) 구현이 끝나면 통과시킨다 — 테스트가 요구사항이다.
6. **force는 "새 것만 추가".** `?force=true&baseRevision=<서버 revision>`이면 조건부 UPDATE는 그대로 통과하고, choices/events의 UNIQUE 충돌만 무시한다. `INSERT IGNORE`는 **모든** 오류를 경고로 바꿔 FK 위반까지 삼키므로, 사전 조회로 이미 있는 seq를 걸러내는 쪽을 권장. (이유를 주석으로.)
7. **REPEATABLE READ에서 위 패턴이 안전한 이유**를 한 문단으로 문서에 남긴다: UPDATE는 항상 최신 커밋된 행에 대해 조건을 평가하고 행 락을 잡는다 (스냅샷이 아니라 "current read"). 그래서 두 트랜잭션 중 하나만 `revision = base`를 만족한다.

## 5. 특이사항

- **락을 쓰지 않는 것이 "하지 않는 것"이다.** 완료 기준이 그 정당성을 증명한다. 비관적 락을 써 보고 싶다면 M9 비교 과제로.
- **신규 슬롯 + baseRevision**: 슬롯이 없을 때 baseRevision은 0이어야 한다. 0이 아니면 400("슬롯이 없는데 base가 있다").
- **`ErrorResponse.detail`의 타입** → **`ConflictResponse`를 따로 뒀다.** `detail`을 `Object`로 넓히면 한 곳의 필요 때문에 나머지 모든 에러 응답의 계약이 느슨해진다. 대가는 에러 형식이 둘이 된다는 것이고 M6에서 통일한다. `code`·`message` 두 필드는 같은 이름으로 맞춰 두어 클라의 분기 방식은 바뀌지 않는다.
- **`ConflictException.current`가 `Object`인 이유**: `common`이 `save`를 알면 의존이 거꾸로 선다. 던지는 쪽이 형식을 정하고 핸들러는 직렬화만 한다. 헐렁한 타입이지만 **방향을 지키는 값이 더 크다.**
- **force 뒤의 이력은 한 기기의 여정이 아니다.** seq는 슬롯 안에서 유일하되 **기기마다 독립적으로 매겨진다.** 충돌 후 force를 쓰면 같은 번호가 서로 다른 선택을 가리킬 수 있고, 그때 **먼저 쓴 쪽이 남고 나중 것은 조용히 사라진다** (`A의 seq 2 = EP02_01/0`, `B의 seq 2 = EP02_03/1` → A만 남음). PLAN이 정의한 "A 이력 유지 + B 새 이력 추가"의 논리적 귀결이라 버그는 아니다. 근본 해결은 seq 대신 기기별 UUID이고, D-010이 미뤄 둔 방향이다 → **재검토 방아쇠**.
- **검증 절차를 두 터미널로 나누지 않았다.** 계획은 그랬지만 이 시나리오는 순차(A가 저장한 *뒤에* B가 낡은 base로 보냄)라 창을 나눌 이유가 없다. 진짜 동시성은 `SaveSlotConcurrencyTest`가 이미 증명하고, 손으로 하는 쪽의 목적은 **응답 본문을 읽는 것**이다. 창을 나누면 변수를 두 번 세팅하게 되는데 그게 M2에서 사람이 단계를 건너뛴 원인이었다.
- **학습 포인트**: 낙관적 동시성, 멱등성의 두 얼굴(재전송 vs 중복), `INSERT IGNORE`의 위험, 격리 수준과 current read.

M3 §7-1의 F23~F29에 이어지는 번호다.

| F31 | **`DATETIME`은 초 단위라 같은 초의 두 쓰기를 구별하지 못한다.** `ON UPDATE CURRENT_TIMESTAMP`는 정상 동작하지만 `updated_at`이 같은 값으로 남는다 | 실행 검증 §4.1~4.4 | **M8**: `updatedAt`을 "언제"로 보여주는 것은 되지만 **어느 것이 최신인지 판정에 쓰면 안 된다.** 충돌 키가 시각이 아니라 revision인 이유 |
| F32 | **409 경로는 revision을 올리지 않는다.** 8회 요청 중 4회만 상승 | 실행 검증 §5 | M3 F29(400은 안 올린다)의 짝. 409는 롤백이 아니라 **애초에 쓰지 않은 것**이다 — 조건부 UPDATE가 0행이면 아무 행도 건드리지 않았다 |
| F33 | **force 뒤의 선택 이력은 두 기기가 섞인 것이다.** seq 충돌 시 먼저 쓴 쪽이 남는다 | 실행 검증 §4.5 + §5 | **M5**: "선택 비율" 집계가 이 데이터를 센다. **M9/M6**: 기기별 UUID로 바꿀지의 근거 |
