## 1. 목표와 한 줄 요약

**Unity 클라가 붙어도 되는 상태.** 비밀번호 해시, 토큰 인증·소유 검증, 관리자 키, 에러 형식 통일, 스키마 결정 마감, README.

끝나면: 토큰 없이 세이브 API → 401, 남의 회차 → 403, DB에 평문 비밀번호 없음, 모든 에러가 같은 형식.

## 2. 선행 조건

- [x] M5 `검증됨` (2026-08-30).
- [x] **PLAN#4 결정** → **D-011**: `(playthrough_id, event_key)` 로 좁힌다. 컬럼은 남기고 UNIQUE 에서만 뺀다.
  - **파생 효과에 주의**: 범위가 넓어져 **409 가 더 자주 난다.** 버전을 올린 뒤의 재도달이 이제 막히고,
    지금 `EventLogRepository.insertAll` 은 중복이면 요청 **전체**가 409 다. M4 가 choices 를 `replayed` 로 흡수했듯
    이벤트도 "이미 있으면 빼고 넣기" 가 필요하다 (M6-2b).
- [x] **PLAN#5 결정** → **D-012**: 도입한다. 그리고 **`game` 을 다시 만든다** (baseline 이 아니라).
  - M0에서 확보한 근거: `game`과 `game_test`에 `schema.sql`을 **손으로 두 번** 적용했다(두 줄을 고쳐 실행 → 되돌리기). M이 진행되며 마이그레이션이 쌓이면 이 수작업이 매번 반복되고, 한쪽만 적용하는 순간 "테스트만 통과/실패"가 난다(ANALYSIS R4).
  - **M1에서 실제로 터졌다** (ANALYSIS §4.1): `game`에 테이블이 `users` 하나뿐이었고, M0는 `users`만 써서 완료 기준을 전부 통과하고도 드러나지 않았다. M1의 `ALTER TABLE`에서야 `Error 1146`으로 나타났다. 게다가 `schema.sql`은 `CREATE TABLE`에 `IF NOT EXISTS`가 없어 **재실행이 불가능**해서, 복구에 별도의 손 SQL이 필요했다(M1 §7-1 F14).
  - **M5에서 한 번 더 쌓였다**: `V3__stats_indexes.sql`을 `game`과 `game_test`에 **손으로 두 번** 적용했다. 그리고 이 파일은 재실행이 불가능하다 — 두 번 돌리면 `1061 Duplicate key name` / `1091 Can't DROP`이다. **"어디까지 적용했나"를 사람이 기억해야 하는 상태**가 M0→M5 내내 이어졌고, 이제 마이그레이션이 V2·V3 둘이라 기억할 것도 늘었다.
  - 따라서 Flyway 도입 시 두 가지를 함께 해결한다: (a) `game`·`game_test` 양쪽에 같은 마이그레이션 자동 적용, (b) `flyway_schema_history`로 **적용 이력이 남아** 드리프트가 조용히 생기지 못하게. `V1__init.sql`은 `schema.sql`에서 **`CREATE DATABASE`/`USE game` 두 줄을 빼고** 옮긴다 (D-012 갱신) — 남기면 `game_test` 마이그레이션이 `USE game` 으로 갈아타 R4 류 드리프트를 만든다. 재실행 가능성 검토는 하지 않는다 — 한 번만 적용되는 것이 마이그레이션의 정의고, 그 한 번은 Flyway 가 보장한다.
  - **인코딩을 명시한다**: `spring.flyway.encoding=UTF-8`. 초안은 "기본값에 맡기면 MS949"(F35 의 일반화)라고 적었는데 **소스 대조에서 틀린 것으로 밝혀졌다** — Boot 의 FlywayProperties 기본값이 이미 UTF-8 이다 (D-012 갱신 4). F35 는 `@SqlConfig` 의 이야기였다. 명시는 유지한다 — 의도 문서화.
- [ ] M0~M5에서 미뤄둔 것 목록 (아래 §9의 "받은 것") 확인.
- [ ] **세션 변수를 건드리는 스크립트에 주의** (M5 §7-1 F34). `SET` 으로 바꾼 세션 변수는 트랜잭션이 아니라 **커넥션**에 붙어 있고, 풀은 그것을 되돌려 주지 않는다. M5에서 seed의 `SET SQL_SAFE_UPDATES = 1`이 무관한 테스트 6건을 죽였다. **"원상복구"는 원래 값을 알 때만 옳다.**

## 3. 숙련자의 사고흐름

1. **Security 전체가 아니라 `spring-security-crypto`만.** 필요한 것은 `BCryptPasswordEncoder` 하나. 전체 Security를 넣으면 필터 체인·CSRF·기본 로그인 페이지가 따라와 학습 범위를 벗어난다. "필요한 최소 의존성" 원칙.
2. **인터셉터 하나로 인증·인가를 다 한다.** `HandlerInterceptor`가 `Authorization: Bearer <token>`을 `sessions`에서 조회 → 만료 확인 → 요청 속성에 `userId`. 경로 패턴은 `/playthroughs/**`, `/users/{id}/**`. 소유 검증(403)은 인터셉터가 아니라 **서비스**에서 (회차의 user_id를 알아야 하므로). 단, `/users/{id}`의 id ≠ 토큰의 userId는 인터셉터에서 바로 403.
3. **토큰은 랜덤 문자열 + DB 행.** JWT는 M6 범위 밖 (PLAN "하지 않는 것"). `sessions(token CHAR(64) PK, user_id, expires_at)`. 토큰은 `SecureRandom` 32바이트 hex. 로그아웃은 행 삭제.
4. **관리자 키는 프로퍼티.** `POST /content/**`는 `X-Admin-Key` 헤더 == `app.admin-key`. 값은 `application-local.properties`. 커밋되는 파일에 기본값을 두지 않는다. **`/stats/**` 도 같은 키가 지킨다** (D-013) — 집계는 관리자용이고(STATUS 6차 점검), 토큰으로 묶으면 로그인한 아무 유저나 전체 통계를 본다. 유저용 요약(`/users/{id}/summary`)은 토큰 경로가 이미 본인 전용으로 만든다.
5. **에러 형식은 "누락 케이스 채우기".** M0의 `ErrorResponse`가 이미 있으므로, `@ExceptionHandler(Exception.class)` → 500 통일, `HttpMessageNotReadableException`(JSON 파싱 실패) → 400, `MethodArgumentTypeMismatchException` → 400, 401/403 전용 예외. 409(`CONFLICT`) 는 `ConflictResponse{code, message, current}` 가 그대로 담당한다 — `detail` 을 `Object` 로 넓히지 않는다는 결정이 이미 있다 (D-004 M4 갱신). **"통일" 은 단일 record 가 아니라 모든 에러가 `code`·`message` 를 갖는 공통 계약이다** (D-004 M6 갱신).
   - **우선순위가 있다.** M2 검증에서 `HttpMessageNotReadableException` 이 실제로 새는 것을 확인했다 — 깨진 JSON 을 보내면 Spring 기본 형식이 나가서 클라가 `code` 로 분기할 수 없다. 이건 "혹시 모를 케이스"가 아니라 **평범한 클라 버그에서 매번 나오는 응답**이므로 M6-8 의 첫 항목으로 잡는다.
   - **응답 `Content-Type` 도 엔드포인트마다 다르다** (M3 검증 §7). `ResponseEntity<String>` 을 쓰는 M1의 콘텐츠 배포는 `StringHttpMessageConverter` 가 처리해 `charset=UTF-8` 이 붙고, 객체를 돌려주는 나머지는 Jackson 컨버터가 처리해 charset 이 없다. **무해하다** — JSON은 규격상 UTF-8이라 charset 을 안 붙이는 쪽이 오히려 정석이고, 실제로 깨진 것은 서버가 아니라 PowerShell 의 디코딩이었다. 다만 "형식 통일"을 하는 M이니 **의도한 차이인지 우연인지 한 번은 결정하고 넘어간다.** (권장: 그대로 둔다. `ResponseEntity<String>` 쪽을 `ResponseEntity<byte[]>` 로 바꾸면 charset 이 사라져 통일되지만, 그 대가로 원본 바이트 배포의 의도가 흐려진다.)
6. **스키마 변경은 마이그레이션으로.** D-011은 `V4__event_once_per_playthrough.sql` — **한 문장 ALTER** 로 드롭과 재생성을 같이 한다. `uk_event_once` 가 playthrough_id FK 를 지탱하는 유일한 선두 인덱스라, DROP 만 따로 실행하면 1553 이다 (D-011 갱신, C8). 기존 데이터 걱정은 순서가 없앤다 — **마이그레이션 파일을 전부 쓴 뒤 재생성**하므로 V4 는 언제나 빈 DB 에 적용된다 (D-012 갱신).
7. **baseline 이 아니라 재생성** (D-012). baseline 은 "V1~V3 는 이미 적용돼 있다고 **믿어라**" 라고 Flyway에게 말하는 것이다. 그 믿음이 틀렸을 때가 정확히 M1의 R4였고, 그때는 `Error 1146`이 날 때까지 아무도 몰랐다. **`seed.sql`이 있으니 재생성 비용이 거의 0**이고, 재생성은 마이그레이션이 **실제로 도는지**를 한 번 증명해 준다 — 이것은 baseline 이 영영 해 주지 못하는 일이다. 따라서 `baseline-on-migrate` 는 쓰지 않는다.
8. **README는 마지막에.** 실행법·API 목록·마일스톤 상태. `docs/`의 내용을 요약하지 말고 링크한다.

## 5. 특이사항

- **첫 의존성 추가 M.** `spring-security-crypto`, Flyway(starter + flyway-mysql). 그 외는 여전히 넣지 않는다.
- **구현 전 소스 대조가 초안을 두 곳 뒤집었다** (2026-08-30, D-012 갱신 3·4):
  - **Boot 4 에는 `spring-boot-starter-flyway` 가 있다.** 아래 "Flyway 의존성 이름" 항목의 교정("그런 스타터는 없다")은 Boot 3 까지의 사실이었다 — 4.0 모듈화 때 스타터가 생겼고, 모듈화 때문에 이제 그 스타터가 **필요**하다(자동 구성이 spring-boot-flyway 모듈에 산다). 두 항목 다 지우지 않는다: "이름을 지어내지 않는다"는 원칙이 **양방향**으로 시험된 기록이다 — 지어낸 이름이 없기도 했고, 없다고 믿은 이름이 생기기도 했다.
  - **`spring.flyway.encoding` 기본값은 이미 UTF-8** (FlywayProperties 소스). C2b 의 "미지정 → MS949"는 틀렸다 — 정정함.
- **포괄 핸들러(M6-8)의 함정 하나를 구현에서 만났다**: `@ExceptionHandler(Exception.class)` 는 Spring MVC 자신의 예외(없는 경로 404, 틀린 메서드 405)까지 가로챈다. 그대로 500 을 주면 "없는 URL 인데 500" 이 된다. Framework 7 의 이런 예외들은 `org.springframework.web.ErrorResponse` 인터페이스로 자기 상태 코드를 들고 있어, **상태는 보존하고 본문만 우리 형식으로** 바꾼다 (GlobalExceptionHandler 주석, ErrorFormatTest).
- **기존 테스트 셋의 의미가 바뀌었다** — "없는 사용자 → 404" 류가 "남의 것 → 403" 으로. 인터셉터가 경로의 id 를 서비스보다 먼저 끊으므로, 서비스의 404 분기(존재하지 않는 사용자)는 HTTP 로 닿을 수 없는 방어 코드가 됐다. 지우지 않는다 — 인터셉터 경로 실수가 생겨도 서비스가 한 번 더 막는다.
- **테스트 78 → 96건.** 늘어난 18 = 보호 자체의 테스트(AuthApiTest 7, ErrorFormatTest 4, 각 영역의 401/403/키 7).
- **기존 API 호환이 깨진다.** M0~M5의 curl 시나리오는 토큰 없이 동작했다. M6 이후 `M{n}-check.md`는 로그인 단계를 앞에 붙여야 한다 → 각 check 문서 머리에 "M6 이후: 토큰 필요" 주석.
- **Flyway 의존성 이름** — 초안에 `spring-boot-starter-flyway` 라고 적어 뒀던 것은 **틀렸다.** 그런 스타터는 없다. 올바른 좌표는 `org.flywaydb:flyway-core` + `org.flywaydb:flyway-mysql` 이고, 버전은 Boot 의 의존성 관리가 정해 준다. **이름을 지어내지 않는다**(PLAN §2.2) 는 원칙이 초안 자신에게 적용된 사례라 지우지 않고 남긴다.
- **학습 포인트**: 인증 vs 인가, 해시 vs 암호화, 인터셉터의 위치(DispatcherServlet 뒤, 컨트롤러 앞), 마이그레이션의 버전 관리(체크섬·이력 테이블·baseline 이 각각 무엇을 보장하고 무엇을 보장하지 않는가).
