**클라 로컬 세이브를 서버에 올리고 새 기기에서 내려받는다. 외래키가 잘못된 세이브를 500이 아니라 404로 막는다.**

## 3. 숙련자의 사고흐름

1. **"upsert"를 DB 문장 하나로 만든다.** `SELECT 후 INSERT or UPDATE`는 두 요청이 겹치면 둘 다 INSERT를 시도해 UNIQUE 위반이 난다. `INSERT … ON DUPLICATE KEY UPDATE`는 `(playthrough_id, slot_no)` UNIQUE를 이용해 원자적으로 처리한다. **UNIQUE 제약이 곧 upsert의 키**라는 것이 M2의 학습.
2. **revision 규칙을 SQL에 정확히 쓴다.** 신규 INSERT 시에는 `ON DUPLICATE KEY UPDATE` 절이 실행되지 않으므로 INSERT 값에 `revision = 1`, UPDATE 절에 `revision = revision + 1`. 응답의 revision은 upsert 후 **다시 SELECT**해서 돌려준다 (M4에서 이 값이 충돌 감지 키가 된다).
3. **FK 위반을 미리 잡는다.** `chapterId + chapterVersion`이 없으면 DB는 FK 위반(500 계열)을 내지만, 클라에게는 "그 콘텐츠 버전이 서버에 없다"(404)가 맞는 답이다. 서비스에서 먼저 조회한다. 단, 조회와 INSERT 사이에 콘텐츠가 삭제될 경쟁은 무시한다 (콘텐츠는 삭제 API가 없다).
4. **기기 등록은 부수 효과.** `deviceKey`로 `devices` upsert (`user_id, device_key` UNIQUE), `last_seen_at` 갱신, id 확보. 사용자가 기기를 등록하는 화면 같은 것은 없다 — 세이브를 올리는 순간 등록된다.
   - 초안에서는 `ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id)` 트릭으로 한 문장에 끝내려 했으나 **두 문장(upsert → SELECT id)으로 바꿨다.** 트릭은 짧지만 "왜 자기 자신을 대입하는가"를 모르면 읽을 수 없고, 이 프로젝트의 규약은 "마법을 쓰지 않는다"(PLAN §0)이다. 같은 트랜잭션·같은 커넥션이라 결과는 같고, 비용은 업로드당 SELECT 한 번이다. **짧은 것과 읽히는 것 중에 읽히는 쪽을 고른 자리**이며, 그 판단 자체를 코드 주석에 남겼다.
5. **스냅샷은 열지 않는다.** 요청 DTO에서 `snapshot`은 `JsonNode`로 받되 어떤 키도 읽지 않고 `writeValueAsString`으로 문자열화해 JSON 컬럼에 넣는다. (PLAN M2 함정. `String`으로 받으면 요청 JSON 안에 JSON 문자열을 이스케이프해 넣어야 해 클라가 불편하다.)
6. **userId는 아직 경로에 노출된다.** M6 인증 전까지 `/users/{userId}/playthroughs`는 누구나 호출 가능. 알고 넘어간다.
7. **서버가 지켜야만 하는 것만 지킨다** (D-008). 슬롯 **개수**는 게임 디자인이고, 슬롯 **번호가 컬럼에 담기는가**는 데이터 무결성이다. 서버는 후자만 본다 — `slot_no`가 `TINYINT`이므로 1..127. 개수 상한은 클라이언트 정책으로 남긴다.
   - 앱에서 먼저 400으로 거르는 이유: 범위를 넘기면 DB는 "Out of range"(500 계열)를 내는데 클라에게 맞는 답은 "번호가 잘못됐다"(400)다. M0의 `BAD_REQUEST` / `CONSTRAINT_VIOLATION` 구분과 같은 층위.
   - 127이 부족해지면 `SMALLINT`로 넓히는 한 줄 마이그레이션이면 된다 (넓히는 방향이라 무해). 지금은 넓히지 않는다.

## 5. 특이사항

- **`INSERT … ON DUPLICATE KEY UPDATE`의 반환값**: 신규 1, 갱신 2, 값이 같아 변경 없으면 0. `revision+1`이 항상 바뀌므로 0은 나오지 않지만, 이 규칙을 모르면 "왜 2가 나오지?"가 된다.
- **`updated_at … ON UPDATE CURRENT_TIMESTAMP`**: 행 값이 실제로 바뀔 때만 갱신. revision이 항상 바뀌므로 문제 없음.
- **JSON 컬럼 왕복**: M1의 PLAN#1 결정이 그대로 적용된다. 스냅샷은 정규화되어 돌아온다 → "의미상 동일"로 검증.
- **목록 API가 스냅샷을 빼는 이유**: 스냅샷은 수십 KB가 될 수 있고 목록은 UI용이다. 쿼리 단계에서 컬럼을 빼는 것과 DTO에서 빼는 것은 네트워크·메모리 비용이 다르다 — SELECT 컬럼 목록을 명시하는 습관.
- **학습 포인트**: UNIQUE = upsert 키. NULL 허용 FK(`device_id`).

## 7. 완료 기준 체크리스트

절차는 `docs/M2-check.md`, 결과는 그 문서 §6 표에.

- [ ] PUT → revision 1. 같은 슬롯 PUT → revision 2. 슬롯 행은 여전히 1개.
- [ ] 없는 `chapterVersion` PUT → **404** (FK 위반 400/500이 아님 — 서비스가 먼저 조회).
- [ ] 없는 회차 PUT → 404. 없는 슬롯 GET → 404.
- [ ] GET의 `snapshot`이 올린 것과 **의미상 동일**하고, JSON 객체로 나온다 (이스케이프된 문자열이 아니라).
- [ ] 목록 응답에 `snapshot`이 **없다**.
- [ ] `deviceKey` 두 종류 → `devices`에 두 행. 같은 기기로 또 올려도 늘지 않는다.
- [ ] `deviceKey` 없이 올려도 슬롯이 만들어지고 목록에서 사라지지 않는다 (LEFT JOIN).
- [ ] 회차 종료가 멱등하다 — 두 번 호출해도 200이고 `endedAt`이 덮이지 않는다.
- [ ] 없는 `userId`로 회차 생성 → 404. 회차가 0개인 사용자 목록 → 빈 배열(404 아님).

**D-008로 바뀐 기준** (PLAN M2의 "슬롯 4 → 400"을 대체):

- [ ] 슬롯 `0` 또는 `128` → **400** (범위 밖. TINYINT 오버플로 500이 아님).
- [ ] 슬롯 `1, 5, 42, 127`을 모두 만들 수 있다 → 목록에 4개. **개수 상한이 없음의 증명.**
