## 1. 목표와 한 줄 요약

**A**: 클라의 새 저장 모델(장면 단위 커밋·회차 갈래·즐겨찾기)이 요구하는 서버 계약을 세운다 — 멱등 회차 생성,
갈래 기록, 즐겨찾기 upsert, 목록 확장, 크기 상한. **B**: 클라가 그 계약을 타고(F6), 새 기기 복구와 409 해소를 완성한다.

A 가 끝나면: PowerShell 로 같은 clientPlaythroughId 를 두 번 POST 해도 회차가 하나, 부모보다 자식이 먼저 와도
`forked_from_id` 가 닫히고, 즐겨찾기가 유저 밑에 올라가 메타 목록으로 내려오며, 1MB 넘는 스냅샷은 413.
B 가 끝나면: 두 기기 시나리오 + 갈라지기·즐겨찾기 왕복.

## 3. 숙련자의 사고흐름

1. **서버가 새로 배우는 것만 센다.** 핸드오프의 큰 변화(장면·롤백·갈래·즐겨찾기)는 클라의 것이고, 서버 관점에서
   남는 것은 셋 — 배치가 커졌다(변화 없음), 회차에 클라 신원과 부모가 생겼다(컬럼 넷), 두 번째 스냅샷이 유저에
   매달린다(테이블 하나). 이 셋 밖의 것을 서버에 넣으려는 유혹(되감기 표식, "활성" 회차, 병합)을 전부 거절한다.
2. **멱등 키는 자원의 클라 측 신원이다.** 요청 UUID 가 아니라 회차 guid(D-019), 즐겨찾기 guid(D-021). 그러면
   재시도·재전송·오프라인 뒤 재접속이 전부 같은 한 문장("있으면 그것, 없으면 만든다")이 된다.
3. **도착 순서를 가정하지 않는다.** 부모 회차가 자식보다 늦게 올 수 있다(D-b) — 클라 id 로 잇고 되채운다(D-020).
   "모르는 부모 거부"는 정확하지만 영영 못 올라오는 갈래를 만든다. 정확함과 완결성이 부딪히면 완결성.
4. **기존 방어선이 그대로 서는지 먼저 확인한다.** `(save_slot_id, seq)` UNIQUE·replayed·409·`(playthrough_id,
   event_key)` UNIQUE — 배치가 커져도, 갈래가 생겨도 한 줄도 안 바뀐다. 바뀌지 않는 것을 확인하는 테스트가 먼저다.
5. **목록은 팬아웃을 조심한다** (M5 user_summary 의 교훈). 회차 목록에 슬롯·즐겨찾기 수가 붙으면
   `playthroughs ⋈ save_slots ⋈ bookmarks` 는 곱해진다. 슬롯은 `slot_no = 1` 로 한정(R5), 즐겨찾기는 상관 서브쿼리.
6. **크기 상한은 뜻이 있는 자리에서 잰다.** 전송 층이 아니라 스냅샷 자체(D-022).

## 5. 특이사항

- **두 레포에 걸친 M 이고 이번엔 서버가 앞이다.** M7 은 클라가 무대였고 서버는 문서만이었다. 이번엔 반대다.
- **의도한 호환 단절 하나**(D-019): `clientPlaythroughId` 필수. F6 전의 클라는 회차 생성에서 400 을 맞는다.
  M6 이 토큰으로 M0~M5 API 를 끊은 것과 같은 종류이고, check 문서 머리에 적는다.
- **바뀌지 않는 것이 더 많다.** `choice_history`·`event_log`·409·replayed·D-015 대조·슬롯 범위 — 전부 그대로.
  이 M 의 테스트 절반은 "그대로인가"다.
- **학습 포인트**: 클라 측 신원으로 멱등 만들기, 도착 순서에 독립인 그래프(되채우기), 두 번째 스냅샷 종류가
  기존 원칙(불투명·크기만)을 그대로 타는 것.
- **구현에서 정해진 것 (09-02)**:
  - 요청의 `forkedFrom.playthroughId`(서버 id)는 **읽지 않는다** — 소유 검증 없는 숫자다. 클라 id 로 같은 사용자 안에서 찾는다(테스트 `부모의_서버_id는_요청이_아니라_조회로_정한다`).
  - 되채우기는 **두 문장**이다 — 갈래(`playthroughs.forked_from_id`)와 즐겨찾기(`bookmarks.playthrough_id`). 둘 다 `PlaythroughService.create` 의 INSERT 직후.
  - 같은 클라 id 의 **동시** POST 는 UNIQUE 가 막고, 진 쪽은 `DuplicateKeyException` 을 잡아 재조회 → 200. 멱등의 마지막 조각.
  - 자기 참조 FK(`forked_from_id`)는 RESTRICT — `DbCleaner`·`seed.sql` 이 DELETE 앞에 `UPDATE … SET forked_from_id = NULL` 한 줄을 가진다.
  - 회차 목록은 이 프로젝트의 **첫 `RowMapper`** 다 — `forkedFrom` 이 중첩 객체라 `query(Class)` 의 평면 매핑으로는 못 만든다. 나머지 조회는 전부 `query(Class)` 그대로.
  - 즐겨찾기 upsert 의 갱신은 **조건 없는 UPDATE** 다(revision 없음) — 지킬 누적 상태가 없어 마지막 쓰기가 이기면 된다. `deleted_at = NULL` 을 같이 써서 부활이 별도 경로가 아니다.
