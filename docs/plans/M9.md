## 3. 숙련자의 사고흐름

1. **화면은 클라이언트다.** Unity 와 같은 자리 — API 가 유일한 계약이고 숫자는 SQL 이 만든다. 화면이 계산하면 검산 지점이 둘이 된다.
   그래서 정적 파일 + `fetch`, Thymeleaf 아님, 외부 스크립트 없음.
2. **통계는 물음이 있을 때만 만든다.** 첫 물음은 언제나 "몇이 시작해서 몇이 끝냈나"다. 그 답을 주려면 "끝냈다"의 정의가 먼저 필요했고,
   그것이 D-025 다. 정의 없는 숫자는 M5 의 "분모가 전체 회차" 사건을 반복한다.
3. **죽은 개념은 지우기보다 표시한다.** `ended_at` 을 지우면 V7·테스트 8건·M2 문서가 움직인다. 두는 비용은 문서 한 줄이다.
4. **회고는 코드가 아니라 고친 기록이다.** 이 프로젝트에서 가장 값있는 것은 "믿었던 것 → 실측 → 정정"의 반복이다(F1~F47). 그것을 M 별로 접는다.
5. **JPA 는 대조 실험으로만.** 기준선이 이미 있다(F30: 조건부 UPDATE 한 문장, 락 없이 10라운드). 같은 테스트를 Hibernate 가 만든 SQL 로
   통과시키고 로그를 나란히 두면 "JPA 가 무엇을 숨기나"가 하루 안에 보인다. 통째 재구현은 그 답을 더 주지 않는다.

## 6. M9-4 JPA 한 조각 — 절차 (선택, 하려면 이 순서)

1. 의존성 `spring-boot-starter-data-jpa`(Boot 4 좌표는 소스로 확인 — F40 의 교훈), `spring.jpa.show-sql=true`, `format_sql`. `ddl-auto` 는 **`validate`** — 스키마는 Flyway 것이다.
2. `jpa/SaveSlotEntity` 하나: `@Version long revision`, `snapshot` 은 `@Convert` 또는 `String`. `@ManyToOne playthrough` 는 **안 붙인다**(id 만) — 조각이지 도메인 모델이 아니다.
3. `PUT /v2/playthroughs/{pid}/saves/{slotNo}` — 서비스는 `SaveSlotService` 의 순서(형식 → 존재 → 재전송 판정 → UPDATE → 이력)를 그대로 옮기되 UPDATE 를 `repository.save()` 로.
4. `SaveSlotConcurrencyTest` 를 `/v2` 로 한 번 더 — 10라운드 "정확히 하나만" 이 나와야 한다. `OptimisticLockException` → 409 매핑 한 줄.
5. 로그의 `update save_slots set … where id=? and revision=?` 를 M4 의 `UPDATE … WHERE revision = :baseRevision` 옆에 놓는다 — 같은 문장인가, 무엇이 다른가(`id` 기준 vs `(playthrough_id, slot_no)` 기준, 그래서 `SELECT` 가 하나 앞서는 것).
6. 회차 목록을 `@OneToMany(slots)` 로 짜 보고 쿼리 수를 센다 — N+1. M5 가 서브쿼리로 푼 팬아웃과 나란히 `docs/M9-jpa.md` 에.

멈추는 기준: 4 가 통과하고 5·6 을 적으면 끝. `/v2` 는 커밋에 남기되 프로필로 끈다.
