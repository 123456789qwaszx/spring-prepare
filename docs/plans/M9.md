## 1. 과제 목록과 제안 순서

| 순서 | 과제 | 왜 이 순서 | 학습 포인트 |
|---|---|---|---|
| 1 | **같은 기능을 JPA로 다시 구현해 `JdbcClient`와 비교** | 부트캠프 2주차가 JPA다. M0~M6를 JDBC로 짠 뒤 JPA로 다시 짜면 "JPA가 무엇을 숨기는가"가 보인다 | 엔티티 매핑, 영속성 컨텍스트, N+1, `@Transactional`과 flush, JSON 컬럼 매핑(`@Convert`), 낙관적 락 `@Version` vs 수동 revision |
| 2 | **콘텐츠 버전 업 시 세이브 마이그레이션 정책** | M1~M4의 설계가 "세이브는 특정 버전을 가리킨다"였다. 이 과제는 그 결정의 대가를 치르는 자리 | 데이터 마이그레이션 정책, 호환 판정(에피소드 ID 유지 여부), 배치 UPDATE |

## 2. 과제 1: JPA 재구현 — 사고흐름

1. **별도 패키지·별도 프로필.** `jpa/` 패키지에 같은 API를 다른 경로(`/v2/**`)로. 같은 DB, 같은 테이블. 프로필로 어느 쪽을 켤지 고른다. 두 구현이 **같은 테스트**를 통과해야 한다 — 테스트를 인터페이스(서비스 계약) 기준으로 재작성.
2. **JPA가 못 하는 것을 먼저 적는다.** `ON DUPLICATE KEY UPDATE`(JPA는 merge = SELECT+UPDATE), `JSON_TABLE` 집계(네이티브 쿼리), 배치 INSERT(`hibernate.jdbc.batch_size` + IDENTITY 전략의 한계). 이 목록이 "왜 이 프로젝트는 JDBC로 시작했나"의 답이다.
3. **낙관적 락 비교.** `@Version`을 `revision`에 붙이면 M4의 조건부 UPDATE를 Hibernate가 생성한다. `OptimisticLockException` → 409. 동시성 테스트(M4-1)를 그대로 돌려 같은 결과를 확인.
4. **로그에서 SQL을 본다.** `spring.jpa.show-sql` + `format_sql`. JDBC 버전과 실행된 SQL을 나란히 비교해 `docs/M9-jpa-vs-jdbc.md`에 기록.
5. **의존성**: `spring-boot-starter-data-jpa` (Boot 4 이름 확인). M6 이후이므로 허용.

## 3. 과제 2: 세이브 마이그레이션 — 사고흐름

1. **정책부터.** "같은 `chapter_id`의 새 버전으로 옮길 수 있는가"의 판정 기준: 세이브의 `current_episode_id`와 이력의 모든 `episode_id`가 새 버전 `chapter_episodes`에 존재하면 호환. 스탯 키 변화는 스냅샷 안이라 서버가 모른다 → **판정은 클라가, 서버는 "옮겨도 되는가"의 최소 검사만**.
2. **API**: `POST /playthroughs/{pid}/saves/{slotNo}/migrate {toVersion}` → 호환 검사 → `chapter_content_id` UPDATE + 이력의 `chapter_content_id` 일괄 UPDATE, 한 트랜잭션. 비호환이면 409 + 어떤 에피소드가 없는지.
3. **FK 복합키가 여기서 빛난다.** `choice_history.(chapter_content_id, episode_id)` FK 덕에 잘못된 마이그레이션은 DB가 거부한다.

## 4. 과제 3: 관리자 통계 화면
