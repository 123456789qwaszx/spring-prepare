# M0. 접속 확인 — 계획서

> PLAN.md §4 M0 기준. 상태 값: `대기` / `진행 중` / `작성됨` / `검증됨` / `수정 중`
> 마지막 갱신: 2026-08-28

## 1. 목표와 한 줄 요약

**Spring → MySQL 왕복이 되고, DB 제약(UNIQUE, NOT NULL, 길이)이 애플리케이션 밖에서 동작한다는 감각을 얻는다.**

끝나면: `POST /users`로 행이 생기고 Workbench에서 보이며, 같은 username은 DB의 UNIQUE가 막아 409로 번역되고, 없는 id는 404다. 이 세 가지가 이후 모든 M의 뼈대(Controller→Service→Repository, 예외→HTTP 번역, 통합 테스트 방식)가 된다.

## 2. 선행 조건

- [ ] 로컬 MySQL 8.x 실행 중, Workbench 접속 가능.
- [ ] `docs/schema.sql`이 `game` DB에 적용됨 (`SHOW TABLES;`에 `users` 포함). **미적용이면 M0-1에서 적용.**
- [ ] `src/main/resources/application-local.properties` 존재 (url/username/password). 확인됨.
- [ ] D-001(Boot 4.1.1), D-002(game_test), D-003(로컬 폴더 전달) 결정 완료. 확인됨.

## 3. 숙련자의 사고흐름 — M0를 받았을 때

M0는 "Hello DB"처럼 보이지만, 숙련자는 여기서 **뒤의 아홉 M이 쓸 틀**을 세운다. 코드 양은 적고 결정은 많다.

1. **빌드부터 의심한다.** 계획서가 말하는 버전과 빌드 파일이 다르면 코드가 아무리 맞아도 안 뜬다. 그래서 첫 작업은 `build.gradle`이고, 첫 완료 기준은 "서버가 뜬다"다. (ANALYSIS §3.1 → D-001)
2. **DB에 먼저 가서 본다.** 앱을 짜기 전에 Workbench에서 `INSERT INTO users …`를 두 번 쳐서 UNIQUE 위반 에러를 **눈으로** 본다. 앱은 그 에러를 HTTP로 번역하는 층일 뿐이라는 감각이 M0의 진짜 목표다. (M0-check.md §1)
3. **예외 번역을 한 곳에 모은다.** `DuplicateKeyException`을 컨트롤러마다 try/catch하면 M6에서 다 걷어내야 한다. 지금 `GlobalExceptionHandler` 한 곳에 두고, 응답 모양(`{code, message, detail}`)도 지금 정한다. (D-004)
4. **얇아도 Service를 둔다.** M0의 Service는 한 줄짜리지만 `@Transactional` 경계를 Service에 두는 규약을 첫 코드에서 지킨다. (D-004)
5. **SQL을 숨기지 않는다.** `JdbcClient`에 문자열 상수를 그대로 넘긴다. ORM이 SQL을 감추면 "DB가 무엇을 했는지"를 못 본다. 그것이 이 프로젝트가 JPA 대신 JDBC를 고른 이유이고, M9에서 JPA로 다시 짜며 비교하는 이유다.
6. **생성 키를 DB에서 받는다.** id를 앱에서 세지 않는다 (실습1·2의 `Collections.max(keySet)+1`은 여기서 끝). `AUTO_INCREMENT` + `KeyHolder`.
7. **테스트는 진짜 DB로.** H2로 통과한 테스트는 MySQL에서 깨질 수 있다 (ON DUPLICATE KEY UPDATE, JSON). 처음부터 `game_test`. (D-002)
8. **M0의 "하지 않는 것"을 지킨다.** 로그인·해시·토큰은 M6. 비밀번호가 평문으로 저장되는 것을 알고도 지금은 넘어간다 — 대신 테스트 값만 쓴다.

## 5. 특이사항

- **M0는 코드보다 결정이 많은 M이다.** D-001~D-005 다섯 개가 여기서 나왔다. 이후 M은 대부분 PLAN의 `[결정 필요]` 하나씩만 다룬다.
- **Boot 4.1.1이라 3.x 강의 자료와 다른 곳**: 스타터 이름(`webmvc`), `@AutoConfigureMockMvc` 패키지, Jackson 3(`tools.jackson`). M0 코드에는 Jackson을 직접 쓰는 곳이 없어 영향이 없고, M1에서 처음 만난다. 번역표는 DECISIONS D-001.
- **기존 실습1·2 코드와의 공존**: `entity/`, `dto/`, `controller/`는 손대지 않는다. 실습3는 `common/`, `user/` 같은 **기능별 패키지**를 새로 판다 (PLAN §2.4). 계층별 패키지(controller/dto/entity) vs 기능별 패키지의 차이를 한 레포에서 비교해 볼 수 있다.
- **`GlobalExceptionHandler`는 전역이다.** `@RestControllerAdvice`는 실습1·2 컨트롤러에도 적용된다. 다만 M0 핸들러는 `NotFoundException`, `BadRequestException`, `DuplicateKeyException`, `DataIntegrityViolationException`만 잡으므로 `MemoController`의 `IllegalArgumentException`은 여전히 500이다. 의도적으로 두었다 — 실습2 동작을 바꾸지 않는다.
- **비밀번호 평문 저장**은 M6까지 의도된 상태. 테스트·수동 확인에 실제 비밀번호를 쓰지 않는다.
- **`created_at`은 DB 시각.** INSERT 문에서 컬럼을 빼야 DEFAULT가 동작한다. 앱에서 `LocalDateTime.now()`를 넣으면 앱 서버 시각이 들어가고, 앱이 여러 대가 되는 순간 시각이 갈린다.
- **Claude는 이 코드를 컴파일하지 못했다.** Spring Boot 4.1.1·Framework 7.0.8 소스로 import와 시그니처를 대조했지만 첫 빌드에서 오타가 나올 수 있다. 그것은 M0-5에서 잡는다.

## 6. 주의사항 (증상 → 원인 → 대응)

| # | 증상 | 원인 | 대응 |
|---|---|---|---|
| C1 | `Could not resolve org.springframework.boot:spring-boot-starter-webmvc` | Gradle이 Boot 4.x BOM을 못 받음 / 플러그인 버전 불일치 | 추측으로 이름을 바꾸지 말 것 (PLAN §2.2). `./gradlew --refresh-dependencies` 후에도 실패하면 에러 전문을 공유 |
| C2 | `Failed to configure a DataSource: 'url' attribute is not specified` | `application-local.properties`가 없거나 프로필이 안 잡힘 | 파일 위치 `src/main/resources/`, `spring.profiles.active=local` 확인. 테스트면 `application-test.properties` 존재 확인 |
| C3 | `Access denied for user` / `Unknown database 'game'` | 접속 정보 오류 / schema.sql 미적용 | Workbench로 같은 계정 접속 확인, M0-check.md §0 |
| C4 | POST가 500, 로그에 `DuplicateKeyException` | `GlobalExceptionHandler`가 스캔 안 됨 | 패키지가 `com.sparta.springprepare` 하위인지, `@RestControllerAdvice`인지 확인 |
| C5 | GET 응답의 `createdAt`이 null (M0 응답엔 없지만 디버깅 시) | record 필드명과 컬럼명 불일치 | `createdAt` ↔ `created_at` 자동 변환은 **언더스코어 규칙**만이다. `createdAtTs` 같은 이름은 매핑 안 됨 |
| C6 | `KeyHolder.getKey()`가 null | INSERT가 AUTO_INCREMENT 키를 반환하지 않음 | `update(keyHolder)`를 썼는지 확인 (`update()`가 아님). MySQL은 `RETURN_GENERATED_KEYS`로 동작 |
| C7 | 테스트에서 `Cannot truncate a table referenced in a foreign key constraint` | MySQL은 FK 부모 TRUNCATE 거부 | `DbCleaner`가 자식→부모 순 DELETE. TRUNCATE 쓰지 않음 (ANALYSIS §3.5) |
| C8 | 테스트가 `game`의 데이터를 지웠다 | 테스트 프로필이 `game`을 가리킴 | `application-test.properties`의 url이 `game_test`인지 확인. `@ActiveProfiles("test")` 누락 여부 |
| C9 | username 31자 POST → 400인데 메시지가 "DB 제약 위반"으로만 나옴 | 앱에서 길이를 검사하지 않음 (D-005 의도) | 정상. 친절한 메시지는 M6 Validation 도입 시 |
| C10 | `contextLoads` 테스트가 CI/새 클론에서 실패 | local 프로필 파일 부재 | 지금 PC에서는 통과. M6에서 정리 (ANALYSIS §3.7) |
| C11 | Location 헤더가 `http://localhost:8080/users/1`이 아니라 `/users/1` | `ResponseEntity.created(URI.create("/users/"+id))` 상대 경로 | 상대 URI도 유효. 절대 URI가 필요하면 `ServletUriComponentsBuilder` — M6에서 |
| C12 | `serverTimezone=Asia/Seoul`인데 `created_at`이 9시간 어긋남 | MySQL 서버 `time_zone`과 URL 설정 불일치 | `SELECT @@global.time_zone, @@session.time_zone, NOW();`로 확인. M3 전에 정리 (ANALYSIS §3.8) |
| C13 | `Name for argument of type [long] not specified, and parameter name information not available` | `@PathVariable long id`처럼 이름을 생략한 파라미터는 컴파일 시 `-parameters`가 필요. Boot Gradle 플러그인이 넣어 주지만 IntelliJ 자체 빌더로 빌드하면 빠질 수 있음 | IntelliJ Settings → Build Tools → Gradle → "Build and run using: **Gradle**" 확인. 또는 `@PathVariable("id")`로 이름 명시 |
| C14 | 한글 문자열이 `???`로 나오거나 `unmappable character for encoding MS949` | JDK 17 javac가 OS 기본 인코딩 사용 | `build.gradle`에 `options.encoding = 'UTF-8'` 추가함 (M0-1). 그래도 나면 파일 자체가 UTF-8인지 IntelliJ 우하단 인코딩 표시 확인 |

## 7-1. M0에서 실제로 확인된 사실 (뒤 M이 전제로 삼아도 되는 것)

| # | 사실 | 어디에 쓰이나 |
|---|---|---|
| F1 | Boot 4.1.1 + Gradle 9.5.1 + JDK 17 toolchain 조합이 동작. 4.x 스타터 이름(`webmvc`)이 해석됨 | 전 M |
| F2 | 기존 실습1·2 코드(Thymeleaf, Lombok)가 Boot 4.x에서 수정 없이 컴파일됨 | 리스크 R3 종결 |
| F3 | `JdbcClient` 자동 등록, `update(KeyHolder)`로 `AUTO_INCREMENT` 수령 | M1~M5 전 레포지토리 |
| F4 | `.query(Record.class)`의 `createdAt` ↔ `created_at` 자동 매핑 동작 | 전 M의 행 매핑 |
| F5 | MySQL `sql_mode`에 `STRICT_TRANS_TABLES`가 켜져 있음 (길이 초과가 저장되지 않고 거부됨) | M1 `display_name` VARCHAR(100), M2 `slot_no` TINYINT |
| F6 | `@ActiveProfiles("test")`가 `spring.profiles.active=local`을 덮어씀. `game_test` 격리 성립 | 전 M의 테스트 |
| F7 | `DbCleaner`의 자식→부모 DELETE가 동작 (TRUNCATE 불필요) | M1~M5에서 테이블 추가만 하면 됨 |
| F8 | `created_at` DB DEFAULT가 KST로 정확히 기록됨 → MySQL 서버 `time_zone`과 URL `serverTimezone=Asia/Seoul`이 일치 | M3 시간대 결정(D-008)의 출발점 |

> **주의 — M0에서 놓친 것 하나.** M0-check §0.1의 "`game`에 테이블 아홉 개가 보이는지 확인"이 실제로는 수행되지 않았고, `game`에는 `users` 하나뿐이었다. M0는 `users`만 쓰므로 통과했고, M1의 마이그레이션 단계에 와서야 드러났다.
> 교훈: **완료 기준이 아닌 "선행 조건 확인"은 통과 여부가 자동으로 드러나지 않는다.** 이후 M의 선행 조건에는 확인 쿼리와 기대 출력을 함께 적는다 (M1-check §0이 그렇게 되어 있다).
