## 1. 목표와 한 줄 요약

**세이브 업로드 한 요청에서 세 테이블(`save_slots`, `choice_history`, `event_log`)이 함께 쓰이고, 하나라도 실패하면 전부 롤백된다. [1] 영구 계층이 실제 데이터로 선다.**

끝나면: 선택 3개 + 이벤트 1개를 동봉한 PUT 한 번에 세 테이블이 채워지고, 그중 하나만 틀려도 revision조차 오르지 않는다. `GET /events`가 챕터 표시명과 함께 나온다 (첫 JOIN).

## 3. 숙련자의 사고흐름

1. **"원자성"을 테스트로 증명한다.** 트랜잭션은 믿는 게 아니라 본다. 완료 기준의 "세 테이블 모두 변화 없음, revision도 안 오름"이 그 증명이다. 테스트는 실패 PUT 후 세 테이블 COUNT와 revision을 모두 확인한다.
2. **검증을 쓰기 전에 끝낸다.** `events[].episodeId`의 `event_key`를 먼저 전부 조회해 하나라도 비면 400 — **INSERT를 시작하기 전에**. 롤백에 기대는 것과 애초에 쓰지 않는 것은 다르다 (롤백은 안전망, 사전 검증은 정상 경로). 단 `choices[].episodeId`가 없는 경우는 FK가 잡아 주므로 사전 조회를 생략할지 결정 — 권장: 사전 조회해서 400 (FK 위반은 M0 규칙상 400이지만 메시지가 불친절).
3. **클라 시각과 서버 시각을 구분한다.** `chosen_at`/`occurred_at`은 클라가 보낸 값(오프라인 플레이), `received_at`은 DB DEFAULT. 두 컬럼이 있는 이유를 잃지 않는다.
4. **배치 INSERT는 M1 도구 재사용.** `NamedParameterJdbcTemplate.batchUpdate`. `choices`가 비어 있으면 배치를 호출하지 않는다 (빈 배열 batchUpdate는 드라이버에 따라 예외).
5. **UNIQUE 위반은 아직 409.** 같은 seq 재전송은 M4에서 흡수한다. 지금은 `DuplicateKeyException` → 409로 끝나는 것을 **확인**하는 것이 M4의 출발점이다.
6. **JOIN은 읽기 API에서 처음 등장한다.** `event_log ⋈ chapter_contents ⋈ chapter_episodes`. 복합 FK `(chapter_content_id, episode_id)` JOIN 조건을 두 컬럼으로 쓰는 연습. 이 쿼리는 M5의 예고편.

## 5. 특이사항

- **첫 복합 FK.** `choice_history.(chapter_content_id, episode_id)` → `chapter_episodes` PK. 단일 컬럼 FK만 보던 눈에 낯설다. "어느 버전의 어느 에피소드"를 한 쌍으로 참조하는 이유를 스키마 주석과 함께 읽는다.
- **`event_log` UNIQUE 범위는 아직 버전별** (`playthrough_id, event_key, chapter_content_id, episode_id`). M6 PLAN#4에서 "회차 내 EventKey당 1회"로 좁힐 수 있다 — 그때 마이그레이션이 필요하므로 지금 데이터를 많이 쌓지 않는다.
- **읽기를 `SaveHistoryService`로 분리했다.** 계획에는 없던 결정이다. 쓰기 경로가 하는 이야기는 "한 요청에서 세 테이블이 함께"라는 트랜잭션 이야기이고, 읽기 경로가 하는 이야기는 JOIN과 증분이다. 한 클래스에 두면 `SaveSlotService`가 두 가지 일을 하게 되고, `@Transactional`과 `@Transactional(readOnly = true)`가 한 파일에 섞인다. **경로가 다르면 클래스도 다르다.**
- **`findState`가 슬롯 `id`를 함께 돌려주게 바꿨다.** `choice_history.save_slot_id`가 필요한데, `ON DUPLICATE KEY UPDATE`는 **갱신 경로에서 생성 키를 주지 않는다**(F18의 이면). 재조회가 유일한 방법이고, 어차피 `revision`을 읽으려고 재조회하고 있었으므로 컬럼 하나를 더 얹는 것으로 끝났다.
- **PUT의 성격이 반쯤 바뀐다.** 스냅샷만 실을 때는 멱등(덮어쓰기)이었지만 `choices`를 함께 실으면 그 부분은 누적이라, 같은 요청을 두 번 보내면 409가 난다. 멱등이 깨진 것처럼 보이지만 깨진 게 아니라 **클라가 `seq`를 다시 매기지 않는 한 같은 요청이 아니게 된 것**이다. M4에서 이 409를 "이미 받았다"(200 replayed)로 바꾸면 회복된다.
- **학습 포인트**: 사전 검증 vs 롤백, 클라 시각 vs 서버 시각, `IN (:list)` 바인딩, 복합 키 JOIN, N+1을 만들지 않는 일괄 조회.

## 7-1. M3에서 확인된 사실

M2 §7-1의 F16~F22에 이어지는 번호다. **F23~F26은 구현 전 문서·소스 대조로 얻은 것**이고, **F27~F29는 실행 검증으로 확인된 것**이다.

| # | 사실 | 근거 | 어디에 쓰이나 |
|---|---|---|---|
| F23 | Connector/J는 `DATETIME`에 대해 **쓰기는 변환하지 않고 읽기는 변환한다.** 쓰기 변환은 대상이 `TIMESTAMP`일 때만 일어난다 | Connector/J 9.7.0 개발자 가이드 "Preserving Time Instants" | `UtcTime.toDbValue`가 존재하는 이유 전부 |
| F24 | `forceConnectionTimeZoneToSession`의 **기본값은 `false`** | 같은 문서 | M2까지의 URL(`serverTimezone=Asia/Seoul`)은 세션 `time_zone`을 **설정한 적이 없다**. KST가 맞았던 것은 서버 기본값이 KST였기 때문 |
| F25 | `serverTimezone`은 `connectionTimeZone`의 별칭(옛 이름)이다 | 같은 문서 | URL 교체가 동작 변경이 아니라 이름 변경 + 플래그 추가임을 설명 |
| F26 | Jackson의 ISO 출력은 **초가 0이면 초를 생략**한다 (`11:30:00` → `11:30`) | `DateTimeFormatter.ISO_LOCAL_TIME` 규칙 | 시각 단언을 문자열로 하면 깨진다 → C9 |
| F27 | **`forceConnectionTimeZoneToSession=true` 가 DB DEFAULT 까지 UTC로 만든다.** `updated_at`(= `CURRENT_TIMESTAMP`)이 한국 시각 21:53에 `12:53:25Z` 로 찍혔다 | 실행 검증 §5.2 | F23·F24가 실제로 그렇게 동작함의 확인. M4~M6의 모든 시각 컬럼이 이 위에 선다 |
| F28 | **오프셋 정규화는 한 방향으로만 일어난다.** `+09:00` 은 −9시간 되고, `Z` 는 그대로다 (이중 변환 없음) | 실행 검증 §5.1 | M7의 Unity가 `Z` 든 로컬 오프셋이든 보내도 된다는 근거 |
| F29 | **한 트랜잭션 안에서 슬롯 upsert 까지 되돌아간다.** 선택 2건 중 1건이 틀린 요청 뒤에 `revision` 1, `play_seconds` 600 그대로 | 실행 검증 §4.4·§5.3 | M4가 "실패한 요청은 흔적을 남기지 않는다"를 전제로 replayed 판정을 세운다 |
