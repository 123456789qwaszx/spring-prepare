# M3. 선택 이력·이벤트 로그 — 계획서

> PLAN.md §4 M3 기준. 상태: **대기**. 마지막 갱신: 2026-08-28 (초안)

---

## 1. 목표와 한 줄 요약

**세이브 업로드 한 요청에서 세 테이블(`save_slots`, `choice_history`, `event_log`)이 함께 쓰이고, 하나라도 실패하면 전부 롤백된다. [1] 영구 계층이 실제 데이터로 선다.**

끝나면: 선택 3개 + 이벤트 1개를 동봉한 PUT 한 번에 세 테이블이 채워지고, 그중 하나만 틀려도 revision조차 오르지 않는다. `GET /events`가 챕터 표시명과 함께 나온다 (첫 JOIN).

## 2. 선행 조건

- [ ] M2 `검증됨`.
- [x] 배치 INSERT 도구는 M1에서 검증됨 — `NamedParameterJdbcTemplate.batchUpdate(sql, SqlParameterSource[])`, 빈 배열은 호출하지 않는다. 구현은 `ChapterContentRepository.insertEpisodes` 참조.
- [ ] `chapter_episodes`에 `event_key`가 비어 있지 않은 노드가 있는 샘플 필요. `qwer.progression.json`의 `EventKey`는 전부 `""` → **테스트용 변형 파일**(예: EP04_01에 `"EventKey": "ENDING_A"`)을 `src/test/resources/content/`에 둔다.
- [ ] 시간대 정리 (ANALYSIS §3.8): `chosenAt`(ISO-8601 UTC) → `DATETIME` 변환 규칙을 D-009로 기록.
  - M0에서 확인된 출발점(F8): `created_at` DB DEFAULT가 KST로 정확히 기록됐다 → MySQL 서버 `time_zone`과 URL `serverTimezone=Asia/Seoul`이 일치한다. **즉 지금 DB는 "KST를 담는 DATETIME"이다.** 클라가 UTC ISO-8601을 보내기 시작하는 M3가 이 전제를 흔드는 첫 지점이다.

## 3. 숙련자의 사고흐름

1. **"원자성"을 테스트로 증명한다.** 트랜잭션은 믿는 게 아니라 본다. 완료 기준의 "세 테이블 모두 변화 없음, revision도 안 오름"이 그 증명이다. 테스트는 실패 PUT 후 세 테이블 COUNT와 revision을 모두 확인한다.
2. **검증을 쓰기 전에 끝낸다.** `events[].episodeId`의 `event_key`를 먼저 전부 조회해 하나라도 비면 400 — **INSERT를 시작하기 전에**. 롤백에 기대는 것과 애초에 쓰지 않는 것은 다르다 (롤백은 안전망, 사전 검증은 정상 경로). 단 `choices[].episodeId`가 없는 경우는 FK가 잡아 주므로 사전 조회를 생략할지 결정 — 권장: 사전 조회해서 400 (FK 위반은 M0 규칙상 400이지만 메시지가 불친절).
3. **클라 시각과 서버 시각을 구분한다.** `chosen_at`/`occurred_at`은 클라가 보낸 값(오프라인 플레이), `received_at`은 DB DEFAULT. 두 컬럼이 있는 이유를 잃지 않는다.
4. **배치 INSERT는 M1 도구 재사용.** `NamedParameterJdbcTemplate.batchUpdate`. `choices`가 비어 있으면 배치를 호출하지 않는다 (빈 배열 batchUpdate는 드라이버에 따라 예외).
5. **UNIQUE 위반은 아직 409.** 같은 seq 재전송은 M4에서 흡수한다. 지금은 `DuplicateKeyException` → 409로 끝나는 것을 **확인**하는 것이 M4의 출발점이다.
6. **JOIN은 읽기 API에서 처음 등장한다.** `event_log ⋈ chapter_contents ⋈ chapter_episodes`. 복합 FK `(chapter_content_id, episode_id)` JOIN 조건을 두 컬럼으로 쓰는 연습. 이 쿼리는 M5의 예고편.

## 5. 특이사항

- **첫 복합 FK.** `choice_history.(chapter_content_id, episode_id)` → `chapter_episodes` PK. 단일 컬럼 FK만 보던 눈에 낯설다. "어느 버전의 어느 에피소드"를 한 쌍으로 참조하는 이유를 스키마 주석과 함께 읽는다.
- **`event_log` UNIQUE 범위는 아직 버전별** (`playthrough_id, event_key, chapter_content_id, episode_id`). M6 PLAN#4에서 "회차 내 EventKey당 1회"로 좁힐 수 있다 — 그때 마이그레이션이 필요하므로 지금 데이터를 많이 쌓지 않는다.
- **학습 포인트**: 사전 검증 vs 롤백, 클라 시각 vs 서버 시각, `IN (:list)` 바인딩, 복합 키 JOIN.

## 7. 완료 기준 체크리스트

- [ ] 선택 3 + 이벤트 1 PUT → 세 테이블 기록, 응답 `acceptedChoices=3, acceptedEvents=1`.
- [ ] `choices` 중 하나의 `episodeId` 오류 → 400, 세 테이블 불변, revision 불변.
- [ ] EventKey 없는 에피소드에 이벤트 → 400.
- [ ] `GET /events`에 `chapterId`, `chapterVersion`, 표시명, `eventKey`, `occurredAt`.
- [ ] 같은 seq 재전송 → 409 (M4에서 바뀔 것을 기록).
