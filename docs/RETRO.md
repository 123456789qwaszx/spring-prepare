# 회고 — spring-prepare 실습3, M0~M9 (2026-08-28 ~ 09-02)

> 무엇을 만들었나: ked(Unity 비주얼 노벨)의 **콘텐츠 창고 + 세이브 금고** 서버. Spring Boot 4.1.1 · JdbcClient · MySQL 8 · Flyway.
> 어떻게 만들었나: M 아홉 개, 각 M 은 계획서 → 코드 → 검증 절차 → 실측 → 정정 → 결정 기록. 결정 27개(D-001~D-027), 확인된 사실 47개(F1~F47), 테스트 120건, 마이그레이션 V1~V6.
> 이 문서는 "무엇을 믿었고, 실측이 무엇을 고쳤나"를 M 별로 접은 것이다. 코드 설명은 각 계획서에, 숫자는 check 문서에 있다.

---

## 1. 한 장 요약

이 프로젝트에서 가장 많이 한 일은 코드를 짜는 것이 아니라 **믿음을 실측으로 바꾸는 것**이었다. 47개의 "확인된 사실" 중 서버가 **데이터를 잘못 쓴** 것은
없다. 서버 쪽 정정은 에러 형식 층 둘(F20·F44 — 잡지 못한 예외가 500 으로 새던 것)뿐이고, 나머지는 전부 **문서의 믿음, 검증 도구, 정의**였다 —
"서버는 틀린 말을 하지 않았다"(F45)가 세 번 반복됐다. 그래서
이 프로젝트의 산출물은 API 스물 몇 개가 아니라, **"이상하면 서버보다 보내는 쪽·읽는 쪽·정의부터 의심한다"는 순서**다.

## 2. M 별 — 믿었던 것 · 틀렸던 것 · 고친 것

|---|---|---|---|---|

## 3. 관통하는 교훈 여섯

1. **정의가 먼저, 숫자는 그다음.** M5 의 "분모가 전체 회차" 사건, M9 의 "끝낸 회차 vs 닫은 회차". 숫자가 틀리는 대부분의 원인은 SQL 이 아니라
   정의이고, 정의 없는 통계는 만들지 않는다 — 물음이 있을 때만 만든다.
2. **서버보다 보내는 쪽·읽는 쪽부터 의심한다.** M3(PS 가 응답 한글을 ISO-8859-1 로), M6(`-Raw` 재인코딩, 비ASCII 헤더), M8(form Content-Type 몰래 붙임).
   세 번 다 서버는 맞았다. 순서를 어긴 건 M8 에서 한 번 — 415 를 보고 문서부터 고쳤다가 테스트가 400 을 내서 되돌렸다.
3. **관대한 매처는 틀린 믿음을 통과시킨다.** `doesNotExist()` 가 null 을 통과시켜 "필드가 빠진다"가 두 M 을 살았다(F46). M5 의 "쿼리 결과를 기대값으로 베끼면
   아무것도 안 지킨다"와 같은 계보. 단언은 믿음의 모양 그대로 못 박는다 — `nullValue()`.
4. **락이 아니라 데이터로 푼다.** 조건부 UPDATE(F30), UNIQUE + `DuplicateKeyException` 재조회(M8 멱등의 마지막 조각), 되채우기 UPDATE 두 문장(도착 순서 독립).
   "정확함과 완결성이 부딪히면 완결성"(모르는 부모도 거절하지 않는다).
5. **바뀌지 않는 것을 테스트한다.** M8 테스트 18건의 절반이 실패 경로와 "안 바뀐 것"(300건 배치, 413 뒤 revision 그대로, 409 8건 그대로). 트랜잭션은 실패했을 때 증명된다(M3).
6. **결정에는 번호를, 사실에는 출처를.** D-001~D-027 이 "왜"를, F1~F47 이 "실측"을 든다. 핸드오프도 계약 정본 한 장(`server-2026-09-02.md`)으로 갈음됐고,
   이견은 "정정한 것 둘"처럼 번호로 오갔다. 대화가 아니라 문서가 계약이다.

## 5. 다음에 다르게 할 것

- **null 규칙을 첫 M 에 못 박는다.** "키가 빠진다/남는다"는 계약의 일부다. M2 에서 매처 하나로 정했으면 F46 은 없었다.
- **검증 도구의 기본값을 먼저 적는다.** PS 5.1 의 인코딩·헤더 기본값이 세 M 에 걸쳐 같은 모양으로 나왔다. 첫 사건 때 "도구 함정" 목록을 만들었으면 나머지 둘은 절차에서 잡혔다.
- **클라와의 계약은 처음부터 "정본 한 장"으로.** M7 은 대화로, M8 은 답신 문서로 했다. 후자가 두 번의 정정을 번호로 남겼고 Unity 쪽 대조가 한 번에 끝났다.
- **죽은 개념은 생기는 순간 표시한다.** `ended_at` 은 M7 에서 이미 클라가 안 부르는 것이 확정됐는데 M9 까지 통계에 남아 seed 논의를 오염시켰다.

## 6. 면접에서 세 문장으로

이 프로젝트는 Unity 비주얼 노벨의 세이브·이력 서버를 JDBC 로 바닥부터 만들면서, **낙관적 동시성(조건부 UPDATE 한 문장)·멱등 생성(클라 측 신원)·
도착 순서에 독립인 갈래 그래프(되채우기)** 를 락 없이 데이터로 풀었습니다. 마일스톤마다 계획서 → 검증 절차 → 실측 → 정정을 기록해 결정 27개와
확인된 사실 47개가 남았고, 그 과정에서 배운 가장 큰 것은 **"이상하면 서버보다 정의·도구·읽는 쪽부터 의심한다"** 는 순서였습니다 — 서버가 데이터를
잘못 쓴 정정은 하나도 없었고, 정정은 전부 문서와 도구와 정의에서 나왔습니다.
