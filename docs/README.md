# docs/ — 문서 지도와 운영 규칙

## 문서 지도

| 문서 | 무엇 | 언제 읽나 | 누가 갱신 |
|---|---|---|---|
| `PLAN.md` | 전체 계획의 **정본**. 배경·역할·규약·M0~M9 목표·완료 기준·열린 결정 | 어떤 M을 시작할 때 해당 절 | 원칙적으로 안 고친다. 계획 자체가 바뀌면 DECISIONS.md에 먼저 쓰고 반영 |
| `schema.sql` | DDL 정본 (v1) | 테이블을 만들 때, 쿼리를 쓸 때 | 변경은 `db/migrations/V{n}__desc.sql`로 (PLAN §3) |
| `ANALYSIS.md` | 코드 쓰기 전 레포·PLAN 대조 결과, 불일치·함정, 리스크 | 새 M 시작 전, 이상한 동작을 만났을 때 | 사실이 바뀌면 |
| `DECISIONS.md` | 결정 기록 D-001… 과 열린 결정 표 | `[결정 필요]`를 만났을 때 | 결정할 때마다 |
| `STATUS.md` | M0~M9 상태 보드, 지금 하는 일, 다음 할 일 | 매번 처음에 | 작업 하나 끝날 때마다 |
| `plans/M{n}.md` | M별 계획서 — 사고흐름, 작업 목록·순서, 특이사항, 주의사항, 완료 기준 체크 | 그 M을 진행하는 동안 계속 | 작업 하나 끝날 때마다 |
| `M{n}-check.md` | 완료 기준을 curl/Postman으로 재현하는 절차 (PLAN §2.6) | 그 M의 검증 단계 | 그 M 구현 중 |

## 운영 규칙 (아미야 ↔ Claude)

1. **한 번에 한 M.** 완료 기준 전부 통과 전에 다음 M 코드를 쓰지 않는다.
2. **작업 하나가 끝날 때마다** 다음을 갱신한다: `plans/M{n}.md`의 작업 표 상태 + 비고, `STATUS.md`의 현재 위치. 결정이 있었으면 `DECISIONS.md`.
3. 작업 상태는 세 단계다.
   - `대기` → `작성됨` (Claude가 파일을 로컬 폴더에 반영) → `검증됨` (아미야가 실행해 기대 결과 확인).
   - 실행 결과가 기대와 다르면 `수정 중`으로 되돌리고 비고에 증상을 적는다.
4. **한 M이 끝나면** `plans/M0.md`~`M9.md` 전체를 다시 읽고 점검한다. 그 M에서 배운 것이 뒤 M의 전제를 바꾸는지 본다 (예: M1에서 JSON 정규화 결정 → M2 스냅샷 처리 방식).
5. `[결정 필요]`는 임의로 정하지 않는다. 선택지·권장·근거를 제시하고 답을 기다린다 (PLAN §0).
6. 커밋은 아미야가 한다. 실제 관행(M0~M5 에서 정착, 2026-08-30 규칙으로 확정): **conventional 스타일로 M당 여러 커밋** — `feat: …` 가 구현, `test(M{n}): 테스트 및 문서 갱신` 이 그 M 의 마감 커밋. PLAN §0 의 `M0: 접속 확인` 형식은 이 관행이 대체했다 — PLAN 은 고치지 않고 이 규칙이 해석을 담당한다.
7. 코드에는 "왜"를 한두 줄 주석으로 남긴다. 마법(리플렉션, 과한 추상화) 금지 (PLAN §0).
8. **테스트는 `./gradlew cleanTest test` 로 돌린다.** 그냥 `test` 는 입력이 안 바뀌었다고 판단하면 조용히 건너뛰고도 `BUILD SUCCESSFUL` 을 낸다 (M2 §7-1 F21). 초록색이 아니라 **작업 요약 줄**(`N executed` vs `N up-to-date`)과 테스트 이름 출력을 읽는다.
9. 검증 절차(`M{n}-check.md`)에는 **선행 조건마다 확인 쿼리와 기대 출력을 함께 적는다.** 완료 기준과 달리 선행 조건은 실패가 조용하다 (ANALYSIS §4.1).
10. **DB에 들어가는 모든 절대 시각은 UTC다** (D-009). 코드에서 `LocalDateTime.now()` 나 시간대 없는 파싱을 쓰지 않는다. 쓰기는 `common/UtcTime.toDbValue`, 읽기는 `OffsetDateTime`. KST는 화면에서만 만든다.
11. **왕복 테스트로 시각을 검증하지 않는다.** 쓰기와 읽기가 같은 방향으로 틀리면 왕복은 통과한다. `DATE_FORMAT` 으로 DB의 벽시계 문자열을 직접 본다 (M3 §6 C8).

## 계획서(`plans/M{n}.md`)의 공통 구조

```
1. 목표와 한 줄 요약          — PLAN에서 가져온 목표 + 이 M이 끝나면 무엇이 가능해지나
2. 선행 조건                  — 이전 M의 완료 기준, 환경 준비
3. 숙련자의 사고흐름          — 이 M을 받았을 때 무엇부터 의심하고, 어떤 순서로 결정하는가
4. 작업 목록과 순서           — 표. 번호, 작업, 산출물, 상태, 비고. 순서에는 이유가 있다
5. 특이사항                   — 이 M만의 성격, 다른 M과 다른 점, 학습 포인트
6. 주의사항                   — 함정. PLAN의 "함정" + 분석에서 찾은 것. 각 항목은 "증상 → 원인 → 대응"
7. 완료 기준 체크리스트       — PLAN의 완료 기준 그대로 + 확인 방법
8. 이 M에서 갱신할 문서       — 어떤 작업이 끝나면 어떤 문서를 고치는지
9. 열린 결정 / 다음 M에 넘기는 것
```
